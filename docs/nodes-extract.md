# Extract nodes

1. **Extract Nodes** (`src/MeshAdapter.Sdk/Nodes/Extract/`): Data retrieval nodes
   - **Reading another tenant of the subtree** (AB#9768, Feature AB#8673): `GetRtEntitiesByType@1`, `GetRtEntitiesById@1`
     and `GetRtEntitiesByWellKnownName@1` take the optional `targetTenant` (`TenantTargetConfiguration`):
     `relation` `Parent` (no id), `Sibling` or `Child` (with `tenantId`, or `tenantIdPath` for an id from the data
     context, only with a verified caller). Without it the node reads its own tenant exactly as before (no guard call). With it the node opens the
     target only through `IMeshEtlContext.OpenTenantAsync` (`Common/TenantReadScope.cs`): the guard checks the relation
     on the tenant registry, proves the node identity's right in the target with the identity service (`Caller` or
     `ServiceAccount`; `System` is always refused) and checks the tenant generation; the read runs on the target's
     repository with the session proven there, and Hidden attributes are checked and dropped with the target's CK
     model. A refusal fails the execution with `CROSS_TENANT_FORBIDDEN` before anything is read. Unknown relations
     (`Descendant`, ...) and the key on any other node (e.g. `ApplyChanges@1`) are refused when the pipeline loads.
     Example:

     ```yaml
     - type: GetRtEntitiesByType@1
       ckTypeId: Basic/Contact
       identity: Caller
       targetTenant:
         relation: Parent
       targetPath: $.contacts
     ```

     Rules and abuse cases: [cross-tenant-access.md](cross-tenant-access.md). Tests:
     `tests/MeshAdapter.Sdk.Tests/Nodes/Extract/GetRtEntitiesCrossTenantNodeTests.cs`,
     `GetRtEntitiesTargetTenantConfigurationTests.cs`, integration
     `tests/MeshAdapter.Sdk.IntegrationTests/Nodes/Extract/GetRtEntitiesCrossTenantIntegrationTests.cs`.
   - **Reading several child tenants at once** (AB#9771, Feature AB#8673): `GetRtEntitiesByType@1` and
     `GetRtEntitiesById@1` take the optional `targetTenants` (`TenantReadSetConfiguration`): `relation: Child` (the only
     relation of v1, the same shape as the fan-out of `ApplyChanges@2`), optional `tenantIds` (without it every
     registered direct child at execution time) and `onRefused` (`Fail`, the default, or `Report`). Not together with
     `targetTenant`; `GetRtEntitiesByWellKnownName@1` has no multi-tenant read (it resolves one entity per item in
     place). Every target is opened through the guard as a `Child` target before anything is read
     (`Common/MultiTenantRead.cs`); each allowed tenant is read with the node's selection, paging, filters and sort
     orders applied per tenant. The output at `targetPath` is a multi-tenant result:

     ```json
     {
       "Items": [ { "RtId": "...", "Attributes": { "InvoiceAmount": 100.0 }, "SourceTenantId": "companya" } ],
       "TotalCount": 3,
       "Tenants": [ { "TenantId": "companya", "TotalCount": 2 }, { "TenantId": "companyb", "TotalCount": 1 } ],
       "RefusedTenants": [ { "TenantId": "companyc", "ErrorCode": "CROSS_TENANT_FORBIDDEN" } ]
     }
     ```

     `SourceTenantId` is added to every entity of `Items`; `TotalCount` is the sum of the tenants' totals. With
     `onRefused: Fail` one refused tenant fails the execution with `CROSS_TENANT_FORBIDDEN`, naming every refused
     tenant, and nothing of any tenant is read. With `Report` the refused tenants are listed in `RefusedTenants` (id and
     code, never the reason) and a warning names each; their data is absent, the others are returned. The identity
     `System` (refused before the child list is read, so also without any child), an invalid configuration and a
     company that could not be verified (registry, identity service or repository unavailable, or no token of the
     pipeline's own service account: `target_unverifiable`) always fail, also with `Report`. An identity service that
     answers and refuses the exchange for one company is a refusal of that company only: `Report` lists it. Example (consolidation in a group):

     ```yaml
     - type: GetRtEntitiesByType@1
       ckTypeId: Accounting/Invoice
       identity: Caller
       targetTenants:
         relation: Child
         onRefused: Report
       targetPath: $.invoices
     - type: SumAggregation@1
       targetPath: $.figures.companya
       aggregations:
         - path: $.invoices.Items[*]
           filterPath: $.SourceTenantId
           comparisonValue: companya
           aggregationPath: $.Attributes.InvoiceAmount
           value: 1
     ```

   - **GetRtEntitiesByTypeNode** (`GetRtEntitiesByType@1`) — entities of one CK type, or (F4.1 criterion 4) with **`ckInterfaceId`** the entities of **all types that implement a CK interface** (derived types included) in one global order. The interface variant is ONE call of the engine method `ITenantRepository.GetRtEntitiesByInterfaceAsync` (read `octo-construction-kit-engine-mongodb/docs/interface-query.md`); the node holds **no expansion, fan-out, merge or security logic** (test: `WithCkInterfaceId_CallsTheSharedEngineMethodOnce_AndNeverTheTypeQuery`). Rules of the node:
     - **Selection**: exactly one of `ckTypeId`/`ckTypeIdPath` or `ckInterfaceId`. `ckInterfaceId` is a **string** (the pipeline YAML serializer has no `RtCkId<CkInterfaceId>` converter) holding the runtime id `Model/Interface`, e.g. `System/Named`; the CK element id with its version (`System/Named-1`) is accepted too. Field filters and sort orders are translated by the same helpers as the type variant, but may only name **members of the interface** and system fields (engine rule).
     - **Paging**: `take` is **required** (one rule for GraphQL and pipelines), `skip` defaults to 0, `skip + take` at most 1000 (engine cap); the type variant keeps its optional `skip`/`take`. `TotalCount` is always filled (the node asks for the count so the output has the type variant's shape; the engine runs one count per collection root).
     - **Output** is the same `IResultSet<RtEntity>` shape as the type variant (`Items`, `TotalCount`); `Items[].CkTypeId` names the concrete type of every row. Rows are untyped `RtEntity`.
     - **Identity and permissions**: same `identity` property and same session classification as the type variant (one session call site in the node file, `Caller` by default); the engine builds the data-permission filter from that session, so a type the caller may not read never appears and is not counted (integration test `ARestrictedCaller_NeverSeesProtectedTypes_AndTheCountDoesNotLeakThem`). The node runs in a transaction session, so the engine queries the collection roots one after the other (accepted by decision).
     - **Failures are language-neutral** (`RtEntitySelectionException`, `Common/RtEntitySelectionException.cs`; the message text is for logs and not the contract): `Code`, `Reason`, `MessageNumber`, `Parameters`. `NODE_CONFIGURATION_INVALID` with reason `CK_TYPE_AND_CK_INTERFACE_BOTH_SET`, `CK_TYPE_OR_CK_INTERFACE_REQUIRED` (also for the type variant without any selection, which used to be a plain `CkTypeIdNotSet` message), `CK_INTERFACE_ID_INVALID`, `TAKE_REQUIRED_FOR_INTERFACE`, `PAGING_NEGATIVE`; parameter `node` always. `INTERFACE_QUERY` for every refusal of the engine: message number **7019**, the engine's reason token (`UnknownInterface`, `TextSearchNotSupported`, `AggregationNotSupported`, `NavigationNotSupported`, `TooManyCollectionRoots`, `PageTooLarge`, `UnknownMember`) and its parameters pass through unchanged (no mapping table, no per-reason numbers); the engine exception is the inner exception. There is no deploy-time validation hook in the pipeline SDK, so these checks run when the node runs (before any session is opened). `TextSearchNotSupported` and `AggregationNotSupported` cannot be caused by this node's configuration (it has no text-search or aggregation option); they are covered by a pass-through test with the engine's own exception factory.
     - **Performance**: no budget of its own; the budget is that of the engine method (one collection at most 1.25x of the type query; indexed multi-collection first page p95 at most 100 ms at 1M entities / 30 roots; unindexed sort field: no promise, **index the sort field** of heavily used interface members in the implementing CK type). The documented local check is `InterfaceVariantAgainstTypeVariant_SameRowCount_PrintsTheRatio` (`Category=Performance`, prints the ratio, asserts only sanity; `OCTO_TEST_SHELF_ENTITIES_PER_TYPE` scales the seed).
     - **Tests**: `tests/MeshAdapter.Sdk.Tests/Nodes/Extract/GetRtEntitiesByTypeNodeInterfaceTests.cs` (hand-over to the engine, validation, pass-through of each reason), `GetRtEntitiesByTypePipelineSchemaTests.cs` (schema: one new optional string property; old- and new-style pipelines deserialize), integration `tests/MeshAdapter.Sdk.IntegrationTests/Nodes/Extract/GetRtEntitiesByInterfaceIntegrationTests.cs` (real orchestrator, real node, real engine on MongoDB; test interface `MeshAdapterIntegrationTest/Shelved-1` implemented by `ShelfBox`, `ShelfCrate` and its derived `ShelfHeavyCrate`; `ShelvedFixture` swaps the data-permission resolver).
   - **GetNumberRangeGapReportNode** (`GetNumberRangeGapReport@1`) — the gap report of a number range
     (`System/AutoIncrement`, by its well-known name `numberRange` or `numberRangePath`) for one fiscal year
     (`fiscalYear` or `fiscalYearPath`; required for a range with fiscal-year periods, left out for one without). The
     node is a thin mapping of the engine method `ITenantRepository.GetNumberRangeGapReportAsync` (read
     `octo-construction-kit-engine-mongodb/docs/number-range-gap-report.md`): it opens the session of its `identity`
     (default `Caller`), calls the method once without a transaction and writes the report to `targetPath` with the
     field names of the asset repository's GraphQL query `runtime.numberRangeGapReport` (`numberRange`, `fiscalYear`,
     `startValue`, `currentValue`, `documentCount`, `missing[{from,to,fromNumber,toNumber}]`,
     `duplicates[{sequenceValue,number,documents[{rtId,ckTypeId}]}]`, `irregular`, `irregularCount`). **Which
     documents it sees** is decided by the session: the engine counts only the documents that identity may read. A
     pipeline usually runs without a verified principal; `Caller` then resolves to the pipeline's service account, and
     without one to the system session, which sees every document of the range - not only those a given user may read.
     A user-facing report that must respect the user's data permissions needs a verified caller (e.g. an HTTP trigger
     with a user token). An unknown range, or one the identity may not read, fails the node; a missing or superfluous
     fiscal year fails it with the engine's message. Example:

     ```yaml
     - type: GetNumberRangeGapReport@1
       numberRange: InvoiceNumber
       fiscalYearPath: $.fiscalYear
       targetPath: $.gapReport
     ```

     Tests: `tests/MeshAdapter.Sdk.Tests/Nodes/Extract/GetNumberRangeGapReportNodeTests.cs` (session of the identity,

   - **GetQueryByIdNode** — Executes a persisted query by RtId. A deleted query (archived, `rtState = Archived`) is `QueryNotFound` like a missing one: the node loads it with the engine's `GetActiveRtEntityByRtIdAsync` (the plain lookup by id returns archived entities too). Resolves the shared `RtPersistentQuery` base, so the caller does not need to know the kind in advance. Supports runtime-data queries (`RtSimpleRtQuery`, `RtAggregationRtQuery`, `RtGroupingAggregationRtQuery`) via `TenantRepository.GetRtEntitiesGraphByTypeAsync`, and **stream-data queries** — simple (`RtSimpleSdQuery`), aggregated (`RtAggregationSdQuery`), grouped-aggregated (`RtGroupingAggregationSdQuery`), and downsampled (`RtDownsamplingSdQuery`) — via the tenant's `IStreamDataRepository` (resolved through `ISystemContext.FindTenantContextAsync(tenantId).GetStreamDataRepository()`, same pattern as `SaveStreamDataInArchive`). Stream-data result shapes mapped into `QueryResult`: simple → **time series** with a leading `Timestamp` column then the projected attribute columns (differs from the runtime simple query, which is one row per entity with no timestamp); aggregated → single row; grouped → one row per group (group-by columns then aggregates); downsampled → **binned time series** with a leading `Timestamp` (bin start) then one column per aggregation, one row per bin (empty bins keep their timestamp and carry null aggregates). Projected values of simple, aggregated and grouped queries are looked up by the physical column name `StreamDataFieldResolver` returns (`CrateDbName`, for example `{base}__v{N}` for a versioned computed column); a downsampling query still derives it — attribute path with dots stripped and lower-cased (`amount.value` → `amountvalue`) — and reads aggregate values by `{physicalColumn}_{funcToken}` (`amountvalue_sum`). Optional `From`/`To`/`Limit` config values override the time range / row cap persisted on the query, and `FromPath`/`ToPath`/`LimitPath` read those same three values from the pipeline data via JSONPath (for ranges computed upstream, e.g. an HTTP trigger) — precedence per value is literal → path → persisted. Values may be ISO-8601 strings or date/time values; a value without a time-zone offset is read as UTC — literals and path values alike, on every stream-data query kind — so the adapter's local zone never shifts the window. A path resolving to nothing falls back to the persisted value with a warning, while a present but non-date (resp. non-integer) value fails the node rather than silently widening the range. `Skip`/`Take` map onto the paginated read (offset / page size) for simple queries and are ignored by the stream-data aggregation / grouped-aggregation paths. **Downsampling** runs `ExecuteDownsamplingQueryAsync`: `From`/`To` plus a positive `Limit` — here the *bucket count*, not a row cap — are mandatory and validated on the node (so a misconfiguration is a pipeline exception, not a storage-layer error), as is a non-empty column list; `Skip`/`Take` page the bins **in memory** because the generated bin axis ignores offset/page size; and the engine clamps the bucket count down to the distinct source bins in range. **Resolution-aware archive selection** is inherent to this query type — there is no switch: every downsampling query is routed through `SeriesResolutionService(GetArchiveRuntimeStore(), new RollupDependencyGraph(GetRollupArchiveRuntimeStore()), GetArchiveCoverageProvider())` — composed per tenant, exactly as the asset-repo GraphQL `streamData.resolveSeriesQuery` and the MCP `resolve_series_query` do; the third argument is the tenant's measured-coverage provider, without which the resolver's coverage filter is silently inert — using the effective `Limit` as target points and the first column's attribute path as the source path. The required aggregation is never guessed: it is the first column's persisted aggregation, or the node's optional `Aggregation` override, which mirrors what a query definition can carry (Count/Minimum/Maximum/Average/Sum) and — when set — replaces the aggregation on *every* column so the values read back match the rollup that was selected. **The result never depends on which archive was read** — `From`/`To`/`Limit` are executed verbatim (the bin geometry is never fitted to the rollup), and a rollup is only accepted when it answers the query *identically* to the persisted archive, so the node and the Refinery Studio can never disagree. Accepted only when all of: the bin width `(To-From)/Limit` is a whole multiple of the rollup's `BucketSize`; `From` sits on the rollup's tick-anchored bucket grid; the alignment is `FixedSize` (calendar rungs can't line up with fixed-width bins); and `LastAggregatedBucketEnd >= To`. Otherwise the persisted archive is read and the failing condition is warned — it is nearly always a fixable query detail. Field example: 7 days / **10** buckets = 16 h 48 min bins over an hourly rollup drops one hour per bin (8 of 168 hours, −4.1 % total, −27 % on a single bin); 7 days / **12** buckets = 14 h bins uses the rollup and matches exactly — pick a `Limit` that divides the range into whole multiples of the bucket size. The archive actually queried is logged at info level with bin width and bucket size. Every non-`Ok` signal warns too — including `CoverageLimited` (the finest rung holds no data at the requested start, so the resolver redirects to a covering coarser rung; the exactness gate alone decides whether that rung is read, so a bin-compatible `FixedSize` fallback IS routed to, a calendar-aligned one is not) — and the resolver's point count never overrides the query's bucket count; `EmptyLadder` / no rollup store fall back to the persisted archive. The node exposes no time-zone option, so the resolver resolves in UTC — irrelevant in practice, since the exactness check rejects calendar-aligned rungs anyway and only fixed-size ones are ever read.
   - **GetStreamDataNode** (`GetStreamData@1`) — Ad-hoc counterpart of `GetQueryById@1`: reads rows straight out of a stream data archive with archive, columns, time range, filters and sorting configured **on the node**, so no persisted query entity is needed. Resolves `IStreamDataRepository` and the `ArchiveSnapshot` via `ISystemContext.FindTenantContextAsync(tenantId)` → `GetStreamDataRepository()` / `GetArchiveRuntimeStore().GetAsync(archiveRtId)`; the snapshot supplies the `TargetCkTypeId` every options object needs plus `UsesWindowedStorage`. Reads via `ExecuteQueryAsync` into a `QueryResult` (leading `Timestamp` column, then the projected columns; on a windowed archive `WindowStart`/`WindowEnd` are inserted after `Timestamp` — those archives alias `window_end` as the time axis and the window columns only reach `StreamDataRow.Values` when projected explicitly). **An unset `Columns` reads the whole archive** — every column of `snapshot.Columns` the resolver accepts, preceded by a `WellKnownName` column taken straight off `StreamDataRow.RtWellKnownName` — so the minimal configuration (just an `archiveRtId`) returns usable data instead of only the time axis. Computed columns are included, addressed by their `Name`; a column mid-backfill is not, because the storage resolver hides it until the backfill commits. A *configured* `Columns` list is honoured as given, except that a name resolving to the time axis or the row window (`Timestamp`, `WindowStart`/`WindowEnd`, or their physical spellings) is dropped — those are emitted for every row anyway, so keeping it would append a second, identical column; a list that reduces to nothing stays explicit rather than becoming "read the whole archive". **Column names — projection, sorting, filtering, grouping — are resolved through the storage layer's own `StreamDataFieldResolver` rather than derived from the attribute path**: `ResolveQueryableColumn` returns `(QueryName, StorageKey)`, the first for the query, the second for reading the value back out of `StreamDataRow.Values`. Deriving the key (dots stripped, lower-cased) worked only by coincidence for a version-0 computed column and returned `null` for every row once a formula change moved it to `{base}__v{N}` — `ComputedColumnNaming` is internal to the CrateDB provider, so the versioned name is not reproducible. Asking the resolver also means "does this column exist" is answered by the same code the query would use, which is why the node can reject an unknown name itself — originally instead of letting the storage layer drop it silently, now simply earlier and with pipeline context. `GetQueryById@1` shares the resolution but treats a missing archive snapshot as non-fatal (warn, standard columns only), because its downsampling path deliberately degrades rather than failing. **`SortOrders` / `FieldFilters` name columns as they appear in the result** (`Timestamp`, `WindowStart`/`WindowEnd`, `WellKnownName`, or any archive column) and the node translates them onto the physical storage columns — `Timestamp` → `window_end` on a windowed archive, which has no `timestamp` column at all. Load-bearing: the storage layer knows only the physical names, so an untranslated `Timestamp`/`WindowStart` never reaches the column it names. The node also **rejects** a name it cannot resolve. That rejection began as a guard against the storage layer dropping such a name without raising anything (`AddSortOrders` / `BuildFieldFilterDtos` both `continue`d past it — a mistyped sort silently returned storage order, a mistyped filter silently returned too many rows); the engine has since fixed that (`StreamDataQueryColumnValidator` rejects for every consumer), which makes the node's translation *more* important — what was silently dropped is now a hard error — and leaves its rejection as the earlier, better-worded of two, since only the node can name the pipeline, the node and the valid names in the caller's own vocabulary. The node therefore rejects any name that is neither a result header nor an archive column and lists the valid ones; `WindowStart` on a *raw* archive is refused too, since that shape has no row window. `WellKnownNames` becomes an ordinary `rtWellKnownName` field filter (`Equals` for one value, `In` for several) — it is a standard column on every archive table; `RtIds` maps onto `WithRtIds`, `Skip`/`Take` onto offset / page size, `Limit` onto the row cap. `From`/`To`/`Limit` may also be read from the pipeline data via `FromPath`/`ToPath`/`LimitPath` (literal wins over path); values without a time-zone offset are read as **UTC**. Both time boundaries are independently optional. Validates on the node — inverted range, non-positive `Limit`, unparsable RtId, archive not found — so a misconfiguration is a pipeline exception, not a storage-layer error. **Gap detection**: setting `GapsTargetPath` additionally writes a coverage report — **per source entity** (`rtId`), so a missing quarter-hour on one meter is not hidden by another meter delivering. `StreamDataGapAnalyzer` (pure, DB-free, in `Nodes/`) clamps every `[window_start, window_end)` to the range, merges overlapping/adjacent ones and reports the uncovered remainder — **coverage/union, not a fixed grid**, so it needs no declared `Period` (a `TimeRangeArchive`'s is advisory and may be null) and handles variable window lengths; a known interval (`ExpectedInterval` → `snapshot.Period`) only adds the counts, without one the ranges are still reported and the node warns once. Runs a **second, separate query** (only `window_start` projected — `window_end` arrives as the row `Timestamp`, the name sits on the row) because the data query's `Limit`/`Skip`/`Take` would hide rows and invent gaps; capped by `MaxGapScanRows` (default 200 000), exceeding it fails rather than reporting from a truncated scan. `RtIds` and field filters are resolved **once** and shared by both queries — they read JSONPath and warn, so a second resolution would duplicate both. Requires `UsesWindowedStorage` and both boundaries; a raw archive is refused. An entity with *no* rows is invisible to a coverage scan — where `RtIds` names it, it is reported as a full-range gap instead. Overlaps are flagged (`hasOverlaps`) and warned about but never fail: legal per the storage concept, yet a sum over them double-counts. **Deliberately no downsampling and no resolution-aware rollup selection**: both live in `GetQueryById@1`, and this node always reads exactly the configured archive.
   - **AggregateStreamDataNode** (`AggregateStreamData@1`) — Condenses archive columns into key figures over a time range (sum of a month's energy, max data quality), optionally grouped (`GroupBy: [rtId]` → one row per source entity). Sibling of `GetStreamData@1`: same archive/filter/time-range resolution via the shared `StreamDataNodeHelpers`, but `Columns`/`SortOrders`/`Skip`/`Take`/`Limit` are **absent** rather than present-and-ignored — meaningless for an aggregation. Dispatches to `ExecuteGroupedAggregationQueryAsync` when `GroupBy` is set, else `ExecuteAggregationQueryAsync`. **Functions: Count/Minimum/Maximum/Average/Sum, and Integral (step integral over [From, To) in value unit x hours, both boundaries required up front, raw archives and rollups with a TimeWeightedAvg, time-range archives refused, mapped in the node's own `MapFunction` and read as `{col}_integral` — deliberately not in the shared `MapStreamAggregation`, which GetQueryById@1 also uses for downsampling/rollup selection)** — `TimeWeightedAverage`/`StateDuration` are refused because they need per-column metadata this node cannot carry (comparison value; the raw archive's LOCF path) and their result keys differ (`_twavg`, two columns on rollups); the error points at `GetQueryById@1` with a persisted per-column query. Result is a `QueryResult`: group-by columns then one column per figure, values read via `ResolveStreamAggregationValue` (`{col}_{token}` + `{Func}_{col}` fallback); the same path aggregated twice gets `{path} ({Function})` headers since the keys are function-unique but bare headers would collide; without `GroupBy` exactly one row is emitted even on an empty result, so consumers always find the expected shape. **`RequireGapFree`** runs `StreamDataGapScanner` (the coverage scan extracted from `GetStreamData@1` so both nodes share query, row cap, interval fallback and overlap warning) **before** aggregating and fails naming the short series — an incomplete month must never return a figure that looks valid but is too low. Overlaps don't fail the guard (legal per the storage concept, and the name promises gap-freedom) but are warned about, since a `SUM` double-counts them. `Average` is arithmetic, not time-weighted. `GroupBy`/`FieldFilters`/`attributePath` go through `ResolveQueryableColumn` — on an aggregation a dropped filter inflates the figure and a dropped group-by column collapses every group into one row — the storage layer rejects both itself since then, but the node's message names the pipeline. One deliberate difference remains: the engine skips a filter carrying **no comparison value** without resolving its name (a tolerated no-op for half-filled filter rows in the query editor), whereas the node validates every configured filter's name regardless — in a pipeline a filter with no value is a mistake, not an unfinished form.
   - **DetectStreamDataGapsNode** (`DetectStreamDataGaps@1`) — Missing time ranges `[start, end)` and missing slot counts per series of ONE windowed archive over `[From, To)`, no row limit. Series via `RtIds`/`RtIdsPath` (required; a series without data is one range over the whole period), `From`/`To` with UTC offset (the offset sets the day boundary; no time zone, day-start or per-day option by design, Markus 2026-11-22), `ExpectedInterval` (default archive period, must be positive), `FieldFilters`. Logic in `Nodes/StreamDataGapDetector.cs`: batches of at most 1000 series (fewer so that days x series stay within 100,000, the CrateDB cap `MaxLocalDaySeriesRows`); per batch one `ExecuteDownsamplingQueryAsync` COUNT(window_start) grouped by rtId in 24-hour bins anchored at `From` (local-day bins, no zone, `BinOrigin` = the UTC time of day of `From`); complete bins are not read, empty bins are missing, partial bins and the sub-day remainder are row-read (`window_start` only, time slices of about 50,000 rows, paged, windows de-duplicated). A refused COUNT (`DownsamplingBinOptionsInvalidException`, e.g. windows across a bin boundary) falls back to the row read for that batch; any other storage failure fails the node. The analysis is `StreamDataGapAnalyzer.AnalyseSeries`, the same as the gap report of `GetStreamData@1`, so ranges and counts agree (parity tests). Output `StreamDataGapDetectionResult`: only series with gaps, sorted by rtId (ordinal) then start. The COUNT shortcut runs only when the archive's declared `Period` equals the slot length (a count means "every slot delivered" only for one-slot windows); otherwise every bin is row-read. Known limit: an archive that declares that period but stores windows of another length (shorter, longer or overlapping) inside a bin whose count equals its slot count hides a hole there. `GetStreamData@1`, `AggregateStreamData@1` and the scanner cap are unchanged.
   - **SftpListNode** (`SftpList@1`) — Lists a remote directory over SFTP and writes one element per matching file to `TargetPath`: `name`, `fullPath`, `length`, `lastWriteTimeUtc` and a `source` object naming the `serverConfiguration`, `remoteDirectory` and `filePattern` the element came from. **Metadata only** — content is read separately with `SftpDownload@1`, so a consumer can drop already-processed files before anything is transferred; listing and downloading in one node would re-fetch every kept file on every run. `FilePattern` is a glob (`*` any run, `?` one character, anchored, case insensitive, every other character literal, `SftpFileNameGlob`); `MinFileAgeSeconds` omits entries still being written. Directory entries are excluded, the result is ordered by name (ordinal), and **an empty result still writes an empty array** because a downstream `ForEach@1` aborts with `PathMustBeArray` on a missing iteration path. `lastWriteTimeUtc` is emitted with an explicit `yyyy-MM-ddTHH:mm:ss.fffffffZ` rather than the round-trip specifier, which renders according to the value's `Kind` and would give a Local value a daylight-saving-dependent offset: consumers derive a file identity from that string, so the same instant has to read identically every time. The `source` stamp exists so a consumer can scope its own bookkeeping without repeating the three connection values in its own configuration. `RemoteDirectory` and `FilePattern` both carry a runtime guard, because `required` is a C# concept the pipeline deserializer does not enforce — an omitted directory would otherwise reach SSH.NET as an empty path. The glob is compiled once per listing rather than per entry. A file under the temporary name of `SftpDelete@1` (`SftpParkedName`: exactly `.<name>.sftpdelete-<32 lower-case hex>`) is skipped, with one warning per listing that counts them, unless `FilePattern` contains `.sftpdelete-` (case-insensitive), so a pattern with a wildcard in front never offers such a file as a delivery. Connection, concurrency limit and host key check come from the shared `ISftpSessionFactory`. **Caveat shared by all four SFTP nodes:** `SftpServerSettings` reads `HostKeyFingerprint`, `ConnectTimeoutSeconds`, `OperationTimeoutSeconds` and `WaitForSlotTimeoutSeconds`, but the CK type `System.Communication/SftpConfiguration` (CCS, `isFinal`) declares none of them, so they never reach the serialized entity and stay at their defaults on every tenant — effective behaviour today is trust-any host key, no per-request timeout, unbounded slot wait. The consumer side is complete and waits on a CCS CK-model change, the same route `MaxConcurrentConnections` took. `OperationTimeoutSeconds` also limits **one protocol request**, not a whole transfer: a slow-but-answering server never trips it.
   - **SftpDownloadNode** (`SftpDownload@1`) — Downloads exactly one file and writes its decoded content to `TargetPath`. Read counterpart of `SftpUpload@1`, which writes exactly one file; designed to run inside a `ForEach@1` over an `SftpList@1` result, one session per file. The remote path is static (`RemotePath`) or resolved from the data context (`RemotePathPath`, takes precedence). `Encoding` defaults to `utf-8` and is validated when the configuration is bound, so a typo fails the deployment rather than the first download; `OnEncodingError` chooses between a lossy read with a warning and failing the node (`SftpContentDecoder`, read counterpart of `SftpContentEncoder`). Single-byte code pages such as ISO-8859-1 map every byte, so the failure path is only reachable for multi-byte encodings. A leading **UTF-8 byte-order mark is stripped** from the decoded string: a BOM is valid UTF-8, so neither the strict pass nor `OnEncodingError` reports it, and kept it becomes an invisible first character that turns a downstream header comparison or split into a silent mismatch — stripped after decoding, not from the bytes, so under a single-byte code page the same three bytes stay the three ordinary characters they are there. **`MaxFileSizeBytes`** (default 100 MiB) bounds what the remote side can make the adapter allocate — the file is held in memory and then decoded to a string, so the peak is roughly 3x the file and a multi-gigabyte drop would take the pod down and repeat on every tick. Enforced twice: against the server's own `GetAttributes().Size` before a byte is transferred, and again while the bytes arrive (`OpenRead` + a hand-written copy rather than `DownloadFile`/`ReadAllBytes`), so a file that grows between the two — or a server that lies about the size — cannot get past it. Non-positive is rejected on the node; there is deliberately no unlimited setting, since the content becomes a `string`. No dry-run branch: reading has no side effects and the downstream chain must see the content in a dry run too. Wiring note: `ForEach@1` seeds the element under its `KeyPath` **default `$.key`**, so `RemotePathPath` reads `$.key.fullPath` unless the loop sets `keyPath` itself.
