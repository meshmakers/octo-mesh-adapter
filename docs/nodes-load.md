# Load nodes

3. **Load Nodes** (`src/MeshAdapter.Sdk/Nodes/Load/`): Data persistence nodes
   - **Writing into another tenant of the subtree** (AB#9769, Feature AB#8673): `ApplyChanges@2` takes the optional
     `targetTenant` (`TenantTargetConfiguration`): `relation` `Parent` (no id), `Sibling` or `Child` (with `tenantId`,
     or `tenantIdPath` for an id from the data context, e.g. the recipient of an invoice; only with a verified caller,
     `ServiceAccount`/`System` name the target statically). Without it the node writes its
     own tenant exactly as before (no guard call). With it the node first opens the target through
     `IMeshEtlContext.OpenTenantAsync` (relation on the tenant registry, the node identity's right in the target proven
     by the identity service — `Caller` or `ServiceAccount`, `System` always refused —, tenant generation); a refusal
     fails the execution with `CROSS_TENANT_FORBIDDEN` before any check reads the target and before anything is
     written, also in a dry run. The write checks (`GenericCreateGuard`, `RtAttributeAccessGuard`) then judge the batch
     with the target's CK model and without the run's method marker (`Common/WriteGuardScope.cs`): MethodOnly
     attributes, inserts of a type whose method replaces the generic create and identity association edges are always
     refused in another tenant. Every association end must be inserted by the same batch or exist in the target (read
     with the proven session), otherwise `CROSS_TENANT_FORBIDDEN` (`cross_tenant_association`). The batch is written in
     one transaction of the target with the proven session; duplicate-key reporting, write-conflict retries and the merge
     of several updates of one entity work as in the own tenant. `ApplyChanges@1` has no `targetTenant`: the key fails
     registration. Example:

     ```yaml
     - type: ApplyChanges@2
       entityUpdatesPath: $._inserts
       identity: Caller            # a target from data needs a verified caller
       targetTenant:
         relation: Sibling
         tenantIdPath: $.invoice.Items[0].Attributes.RecipientTenantId
     ```

     Tests: `ApplyChangesCrossTenantNodeTests`, `ApplyChangesCrossTenantIntegrationTests` (real tenant tree in MongoDB:
     a released invoice of A becomes an incoming document in B, then update and delete; refusals leave B unchanged).
     Design and abuse cases: `docs/cross-tenant-access.md`.
   - **Master-data sync into the child tenants** (AB#9770, Feature AB#8673): `ApplyChanges@2` takes the optional
     `targetTenants` (`TenantSetConfiguration`: `relation: Child`, optional `tenantIds`; not together with
     `targetTenant`). Without `tenantIds` the targets are the registered direct children of the pipeline's tenant
     (`IMeshEtlContext.ListChildTenantsAsync`, the guard's registry snapshot, cached up to 30 s). Every target is opened
     through `OpenTenantAsync` as a `Child` target and written in its own transaction with the proven session: the node
     reads the existing copies, plans an insert (missing copy) or update (this sync's copy) per entity — a replace of
     the source replaces this sync's copy as a whole, so an attribute the replace leaves out is gone from the copy
     too — or a delete (a delete of a missing copy writes nothing); several changes of one entity in a batch are
     applied in order (updates merged, the later value winning; a replace or delete ends what came before), stamps `RtSyncOrigin` (source tenant = the pipeline's tenant, source
     RtId, `SyncedAt`) and drops any origin of the input, judges the plan with the target's write guards and writes it.
     An entity under that RtId without this origin refuses the whole target (`SYNC_OWNED_ENTITY`). Failures are
     collected; after the last target the node throws `CrossTenantWriteFailedException` (`CROSS_TENANT_WRITE_FAILED`,
     every failed target with its stable code, the written ones). Not supported with `targetTenants`:
     `associationUpdatesPath`, `onDuplicateKey: Report`, record array item updates and secret clears (configuration
     error). Dry run: nothing written, the intent lists per target the planned inserts, updates and deletes.
     **Sync-origin write rules**: enforced by the engine (octo-construction-kit-engine-mongodb
     `SyncOriginWriteRules`) for every writer, `ApplyChanges@1` and `ApplyChanges@2` included: a write of
     `RtSyncOrigin` (a value, an array item update or a secret clear) and an update, replace, delete or archive of an
     entity that carries an origin are refused before anything is written; the nodes report it as
     `SYNC_OWNED_ENTITY` (`Common/SyncOriginGuard.cs`, `SyncOriginRefusal`). The sync writes with a sync-writer session
     of the pipeline's tenant, which writes only that source's copies. A dry run does not judge it. Example
     (sync pipeline of the group tenant):

     ```yaml
     triggers:
       - type: FromWatchRtEntity@1
         ckTypeId: Acme.Crm/Contact
         updateTypes: Insert, Update, Replace
     transformations:
       - type: CreateUpdateInfo@1
         targetPath: $._sync
         targetValueKind: Array
         updateKind: UPDATE
         ckTypeId: Acme.Crm/Contact
         rtIdPath: $.Document.RtId
         attributeUpdates:
           - attributeName: Name
             attributeValueType: String
             valuePath: $.Document.Attributes.Name
       - type: ApplyChanges@2
         identity: ServiceAccount
         entityUpdatesPath: $._sync
         targetTenants:
           relation: Child
     ```

     Deletions: the default delete in the source archives the entity (update event, `$.Document.RtState` 1); an
     erase is a delete event, which `FromWatchRtEntity@1` delivers only with `includeDeletes: true` (`$.UpdateType` 8,
     `$.DocumentRtId`). Both delete the copies; the full pipeline with its `If@1` branches is in
     `docs/cross-tenant-access.md` 4.1b. A
     single-`targetTenant` write whose target engine refuses the batch fails with `CROSS_TENANT_WRITE_FAILED`
     (`VALIDATION_FAILED`); own-tenant writes still only log it.
     Tests: `ApplyChangesSyncNodeTests`, `MasterDataSyncIntegrationTests` (real tenant tree and the real change stream
     of the group tenant: create, change and delete reach A and B within 60 s each; idempotency, owner, refusal of B,
     local entities untouched, forged origins).
   - ApplyChangesNode/ApplyChangesNode2 — `ApplyChanges@2` merges several updates of one entity into one (later value wins; Secret clear lists reconcile). **Conflict detection is structural:** `AttributeValueComparer` compares lists, dictionaries, `RtRecord`s and `JsonElement`/`JsonNode` trees by content and numbers by value (int/long/decimal/double), so equal content never warns (it used to use reference `Equals`, ~90k false WARN/day on `Loxone/Control.States`). A real conflict logs ONE warning per entity and batch listing all conflicting attributes with compact, 200-char-truncated values; attributes named like credentials (`password`, `secret`, `token`, `apikey`, …) and `RtSecretValue`s print `<redacted>`. **Concurrent writers:** a MongoDB WriteConflict (112) is detected **anywhere in the exception chain** (`IsWriteConflict`; the repository wraps it in `OperationFailedException`, so the old unwrapped-only catch let it fail the pipeline), the transaction is aborted (`AbortQuietlyAsync`) and the write retried on a fresh session, at most `MaxWriteAttempts` = 6 with a jittered exponential wait (`WriteConflictBackoff`: ceilings 25..400 ms, half to all of it, ~0.4-0.8 s total; the semaphore is released for the wait and re-acquired before the next attempt, so other writes of the adapter go on, test `The_backoff_releases_the_process_wide_lock_so_other_writes_go_on`). 🔴 A conflict that outlasts the retries is **never a silent success** (the old loop ended without error and without flag): with `onDuplicateKey: Report` + `duplicateKeyTargetPath` it writes the flag `true` (nothing written), otherwise it rethrows. The duplicate-key filter runs before the conflict filter. The process-wide semaphore serialises only one adapter; two replicas meet 112 (cross-replica case covered by `SlotBookingConflictTests`, Testcontainers, sample method pipeline `docs/examples/slot-booking-method.yaml` with the declared method error `CONCURRENT_CHANGE`). Each attempt's session is disposed. A unique index belongs in the CK type's first version: adding one to a type with data is a Major change. Details: `docs/developer-guide.md` "Unique keys and concurrent writers".
   - **Origin of archive rows**: the three archive load nodes take `Origin` (`Automated` default / `Manual`), `ManualReason`, (raw + time-range) `ManualReasonAttributePath` and the per-row reason from the request data: `ManualReasonPath` (raw + time-range, relative to each item at `Path`) / `ManualReasonProperty` (series, on each value); order per row: request data, attribute, static `ManualReason`. `ArchiveWriteOriginStamp` validates once per node run: a manual write records as writer the verified caller's readable name (`VerifiedPrincipal.Name`, else its subject id), else the client id of the pipeline's service identity (`IMeshEtlContext.GetServiceIdentitySubjectIdAsync`), else `pipeline:<rtId>` — never refused, never empty; a reason without `Manual` is refused. Write result: `ArchiveWriteResultReporter` warns with the rows not stored per reason (only automated `CkTypeMismatch` skips are logged at Debug instead: one update list fanned out to one node per archive skips the other CK types on every run), stores `{stored, skipped, skippedByReason}` at `WriteResultPath`, and fails with `FailOnSkippedRows`. See `docs/developer-guide.md`, *Origin of archive rows*.
   - SaveStreamDataInArchive — writes instant measurements to a raw archive. A record attribute is handed on as one value; the engine repository expands it into the member columns (needs engine-mongodb with that fix). Chain test against the real repository: `RawArchiveRecordMemberPipelineIntegrationTests` (`StreamDataPipelineFixture` = `StreamDataFixture` + `AddOctoMeshAdapter`).
   - **SaveTimeRangeStreamDataInArchive** (`SaveTimeRangeStreamDataInArchive@1`) — writes rows that already carry an `rtid` to a windowed archive. Post-hoc **orphan guard**: the distinct source rtIds of the batch are looked up (system session — a read filter would turn "you may not see it" into "it does not exist" and refuse good measurements) and the whole insert is refused if any is missing.
   - **SaveTimeRangeSeriesInArchiveNode** (`SaveTimeRangeSeriesInArchive@1`) — ingests a whole windowed **series** in one node: it resolves each series' anchor entity by well-known name, creates the missing ones plus their parent association, advances the existing ones to the series' newest window, and only then bulk-inserts every value as an archive row. It exists because the node composition it replaces materialises one runtime entity per measured window to write one row — measured on a real EDA replay: 316,268 windows in 4,530 s (78 rows/s, 12.8 ms per window) with the database nowhere near the bottleneck, against 16 anchors and 0.79 ms per row afterwards.
     - 🔴 **No orphan rows by construction, not by check.** The anchor resolution runs first and is the only producer of an `rtid`: every one handed to the archive was either read from the runtime store or written and confirmed, and a failed anchor write aborts the transaction and **throws** rather than continuing. Keep that order and keep the failure hard — the post-hoc guard of the sibling node above does not apply here, because this node calls `InsertTimeRangeAsync` directly.
     - The **parent** rtId is parsed from the document and not checked for existence; the EC pipeline covers that upstream (`GetRtEntitiesByType@1` + `Join@1`, unknown metering points answered with ABLEHNUNG_CRMSG). A pipeline that feeds it parent ids from elsewhere has to establish that itself.
     - **Ordering between two deliveries for the same window is not this node's business** — it belongs to the archive's `Archive.ConflictPrecedence` (System.StreamData 1.13.0). The node's part is mapping the ranking columns (a quality code, the source document's own date) into the archive alongside the values.
     - 🔴 **Date columns are stored in UTC, like the window boundaries.** A date string with an offset (`+02:00` — one grid operator writes `DocumentCreationDateTime` that way, the others write `Z`) parses to a *local* `DateTime`; passed through, the archive stored that wall clock as UTC, off by the host's offset. Invisible in a UTC container, two hours off when the EDA adapter ran on a CEST laptop during a rehearsal (199,180 rows with a shifted `SourceDocumentDate`, values unaffected). `TimeRangeSeriesShaper.ColumnScalar` normalises every column value that is a date.
     - **Enum columns store the integer CK key, not the name.** A node that skips the RtEntity round trip has to convert `"L1"` → `1` itself or every write fails on a CrateDB cast; `ConvertColumnValue` routes through `RtPathEvaluator` on a scratch entity (memoised per column+value) rather than re-implementing the rule.
     - The shaping rules (anchor key, which value the anchor reflects, which values are unusable) live in the pure `TimeRangeSeriesShaper` so they are testable without a CK model or a database.
     - 🔴 **An explicit null is a value, a missing property is not.** The archive keeps the stored value of a column a row does not name and clears a column named with null, so `TimeRangeSeriesShaper.TryReadColumn` puts a JSON `null` on the row as a named column with null and leaves a missing property (and an object, array or unconvertible value) unnamed. Do not collapse them with a `scalar is not null` check again: a null would then stop clearing the stored column. The raw and time-range save nodes keep the same distinction through `CreateUpdateInfo@1` and the data context (`ArchiveNullVersusMissingChainTests`); rule and limits in `docs/developer-guide.md`, "Partial delivery". Today a null on an optional enum reaches the archive as a named null. A null on a member of a record the update does not hold yet (`Amount.Value` without `Amount`) does so only when the node sets `ExplicitNullCreatesRecords` (default `false`; then `RtPathNullHandling.CreateMissingRecords`). Keep the default off: for a runtime entity the created record would replace the stored one and lose its other members.
     - 🔴 **Series-scoped column values come from the source object each value came from** (`ShapedSeries.SourceOf`), not from the first object merged under the key. Several objects share a key whenever one batch carries several documents for the same register, and their series-scoped values differ — above all the document date the archive's ConflictPrecedence orders by. Taking them from the first object stamped every row of a batch with the first document's date, so a same-quality correction in the same batch won or lost by position; found on a replay, where 303,788 of 324,236 rows carried a document date other than the one the precedence rule selects (values were unaffected only because the corrections there were identical re-sends). The anchor reads them from the winning value's source for the same reason.
   - EMailSenderNode
   - **EMailSenderNode2** (`SendEMail@2`) — v1 carries exactly one attachment, described by four sibling properties, and gives the body no way to address it, so a billing dispatch spends its only slot on the invoice PDF and cannot also show the community logo. v2 replaces those four properties with an `Attachments` list whose entries may declare a `ContentId`; such an entry becomes a `LinkedResource` on the HTML `AlternateView`, which is what makes `cid:` resolve in Outlook and Gmail — an image pointed at by URL needs a bearer token the mail client does not have, and a `data:` URI is stripped by both. **An inline entry is only fetched when the rendered body actually addresses its content id**, so a pipeline may attach a logo unconditionally without every mail paying for it; the body is therefore rendered before attachments are resolved. An optional inline entry that is missing has its `<img>` stripped from the HTML rather than leaving a broken image. `FileName`/`FileNamePath` apply to file attachments only — a linked resource carries no `Content-Disposition` and is identified by its content id alone; `ContentType`/`ContentTypePath` apply to both, and reading the type from the stored binary matters because an operator can replace a PNG logo with a JPEG at any time. `BodyFormat` (Markdown / PlainText / Html) says what the body at `Path` is, and `BodyFormatPath` reads a NotificationTemplate's `RenderingType` so the template's own declaration wins — v1 ran Markdig over every body regardless, which is why a template declaring PLAIN was still sent as converted HTML. The Markdig pipeline deliberately drops `GenericAttributesExtension`: it reads a trailing `{...}` as HTML attributes, so an unfilled `${customer.iban}` reached the recipient as a bare `$` with the token's text moved onto the paragraph. `ReplyToPath`/`ReplyToAddress` cover the common case of sending from a no-reply mailbox while wanting answers elsewhere. A text/plain alternative is emitted beside the HTML (v1 sent HTML alone), with `cid:` image markup removed since no text-only reader can resolve it — for a **Markdown** body only, and HTML-decoded, so the two halves of one mail say the same thing: the resolver escapes substituted values for the markup path, and without decoding a company name of `Müller & Söhne` reached the text reader as `Müller &amp; Söhne`. A **plain** body is literal text and is passed through untouched. Streams opened for already-resolved attachments are disposed if a later one throws: they are otherwise owned by the `MailMessage`, which does not exist yet while attachments are being resolved, so an exception outside the two the loop handles (a Mongo timeout, a cancellation) stranded every stream before it.
   - SftpUploadNode
   - **CommitNotificationStateNode** (`CommitNotificationState@1`) — after `SendEMail@2`: the prepared `processedUntil` / `sentRows` / `queryRtId` become the delivery state's `ProcessedUntil` / `SentRows` / `QueryRtId`, `LastRunAt`/`LastSentAt` are stamped, `LastError` and the lease are cleared. A failed send never reaches it, so a later tick sends again: delivery is at least once, never lost, and a send whose result is ambiguous (the server accepted the mail but the call failed) can repeat rows more than once. It sets `sent` on the prepared notification before its write, which is what lets `PrepareNotification@1` record the rows when this write fails, and updates the state named by `stateRtId`, which `PrepareNotification@1` always sets when it takes the lease; a prepared notification without it fails the node. Honours dry run (`DryRunHonouredLoadNodes.CommitNotificationState`): the intent carries `preferenceRtId`, `newCount` and `sentRowCount`, and nothing is written.
   - **SftpDeleteNode** (`SftpDelete@1`) - Deletes exactly one file over SFTP through the same `ISftpSessionFactory` as `SftpList@1` / `SftpDownload@1` / `SftpUpload@1`, so the per-server concurrency limit and the host key check apply to deletion as well. The path is static (`RemotePath`) or read from the data context (`RemotePathPath`, takes precedence), and a path ending in `/` is refused before connecting - this node removes a file, not a directory. `ISftpSession.Delete` returns **false** when the file was already gone rather than raising: that is a state, not a transport failure, and it keeps SSH.NET's `SftpPathNotFoundException` behind the seam the way `EnsureDirectory` already does. What to make of it is the pipeline's call: `OnMissingFile` defaults to **`Fail`**, while `Ignore` logs a warning and carries on, which is what a run repeated after a partial pass wants - and it covers what the server reports as a missing path, not a server that answers with a generic failure. Honours dry run (`DryRunHonouredLoadNodes.SftpDelete`): the intent carries host, port, user, path and the mode, and nothing is deleted. Without an expected identity every other failure becomes `CannotDeleteViaSftp` naming the node, while an exception the session factory already worded (host key mismatch, slot wait) passes through unwrapped. **Expected identity:** `ExpectedLength`/`ExpectedLengthPath` and `ExpectedLastWriteTimeUtc`/`ExpectedLastWriteTimeUtcPath` (the `length` and `lastWriteTimeUtc` of an `SftpList@1` element; a path that is set decides alone, blank or not, and never falls back to the static value; a key with an empty YAML value, `~` or `null` is null and counts as not set) make the node delete the file only while it is still the file that was listed; `OnIdentityMismatch` `Fail` (default, zero member) or `Warn` (deliberately no member that deletes anyway). `Warn` without an identity, YAML null keys included, is refused before connecting and in a dry run (`SftpDeleteWarnWithoutIdentity`): ignored, it would delete unchecked behind a setting that says otherwise; `Fail` cannot be told from the default and stays accepted. Unset, the node runs the plain `Delete` path exactly as before (same requests, same dry-run intent). Set: `ISftpSession.GetEntry(P)` first (LSTAT; missing -> `OnMissingFile`; different or a directory -> nothing moved, `OnIdentityMismatch`); only on a match `ISftpSession.MoveToNewName(P, SftpParkedName.PathFor(P))` (`<dir>/.<name>.sftpdelete-<guid N>`) (`posix-rename@openssh.com` where offered, an atomic rename(2); plain SSH_FXP_RENAME when SSH.NET raises `NotSupportedException`), `GetEntry` there again and `Delete` there. **Nothing is ever renamed back**, so no step writes to the listed name and no newer file under it can be replaced on any server. A mismatch after the move (replaced between check and move, or a rename that changed length or time) and every failure after the move leave the file under the temporary name and fail the node whatever `OnIdentityMismatch` says, with one of three texts that say what is there and what is safe (`CannotDeleteMovedAsideViaSftp`: the checked listed file, gone already if only the answer was lost, deleting it there is safe; `SftpReplacedFileLeftAside`: not the listed identity - an unread replacement or a rename that changed the values - compare before deleting; `SftpMovedAsideFileUnchecked`: unknown, names the listed identity; `CannotMoveAsideViaSftp` names the likely causes and the listed identity) - none advises a rename onto the listed name unless it is free. Values are validated before connecting and before the dry-run branch: both halves or neither, blank paths refused (`SftpDeleteIdentityPathBlank`), length a JSON integer or digit string >= 0 (no reals, signs, spaces), time read with `GetValue(path, parseDateStrings: false)` and matched against `yyyy-MM-ddTHH:mm:ss[.f{1,7}]Z` (ASCII digits, upper-case `T` and `Z`, `\z` anchor) before an exact parse without the `Z`, so the pod's time zone never enters; a refused text longer than 32 characters is named by its length only, and `0001-01-01T00:00:00Z` (what `SftpList@1` writes when the server reports no time) is refused (`SftpDeleteIdentityTimeNotReported`). Needs the right to rename and delete in the file's directory, a rename that keeps length and last write time, and a listing and LSTAT that report the same values. Measured in `SftpDeleteIdentityIntegrationTests` (Testcontainers, OpenSSH 8.4p1 and SFTPGo 2.7.5, images pinned by digest): listing and LSTAT agree to the tick, the move keeps both values, OpenSSH offers the POSIX rename and SFTPGo does not; a symbolic link under P: on OpenSSH every request addresses its target (REALPATH), so nothing moves unless the target has the link's length and second - then the target is moved and deleted, as the plain delete deletes it; on SFTPGo the link is deleted and its target stays. Limits: content is not compared; a file under the temporary name is not recovered by a later run (`SftpList@1` skips it with a warning unless its pattern contains `.sftpdelete-`); the temporary name adds 45 ASCII characters, so a name over 210 bytes in UTF-8 fails at the move where names are limited to 255 bytes, as on both measured servers (`Node_TheLimitOfANameCountsBytes_210FitWithTheTemporaryName_211DoNot`); without the POSIX request the move is only as atomic as the server's plain rename (OpenSSH's is link() plus unlink()). Unit tests: `SftpDeleteNodeIdentityTests` against `InMemorySftpServer` (asserts what is left on the server; `After` stands in for a request carried out whose answer was lost; YAML null at the boundary through the real serializer; the guide's loop through the real `ForEach@1` over a real `SftpList@1` result), `SftpDeleteNodeIdentityConfigurationTests` (defaults, schema, YAML, misspelled options refused naming the option), `SftpParkedNameTests` (the form, strictly), `SftpListNodeParkedNameTests` (skip, warning, the exception through the pattern).
   - **DeployPipelineNode** — Deploys a specific pipeline within the same data flow via the Communication Controller REST API. Uses `ServiceAccountConfiguration` for OAuth2 authentication: 🔴 the account's token comes from `AcquireServiceAccountTokenAsync` and goes to a client of its own (`IServiceAccountCommunicationClientFactory`, same endpoint and tenant route as the `ICommunicationServicesClient` singleton) — never into the process-wide `IServiceClientAccessToken`, which the singleton reads. **Fail-closed:** no token → node error, nothing deployed, chain stops (before, the call went out with whatever the shared holder carried, often the adapter's own token). Tests `DeployPipelineNodeEnabledGuardTests` (identity section). Safety: cannot deploy self, must be in same data flow. **A pipeline whose `System/Enabled` is explicitly `false` is SKIPPED, not deployed** — `DeployDataFlow` has always dropped disabled pipelines from the configuration it pushes, so on that path a disabled pipeline is an undeployed one, while this node went straight to the controller and would register it and start its triggers. That matters the moment a pipeline deploys another one to hand it fresh settings (the import-window recompute is the first): without the guard it resurrects an import nobody enabled, on every tenant that has the pipeline but never turned it on. Skipped rather than failed, because "the operator switched it off" is a normal state the calling pipeline cannot repair; an absent attribute is not a disabled pipeline, so nothing that worked before changes.
   - **TeamsBotReplyNode** (`TeamsBotReply@1`) — sends a reply into a Microsoft Teams conversation via the Bot Framework REST API (`POST {serviceUrl}/v3/conversations/{conversationId}/activities`). Bot token via client-credentials against the `botframework.com` authority; credentials read from a `MicrosoftGraphConfiguration` (its ClientId/ClientSecret double as the bot App ID/secret). Outbound counterpart of `FromTeamsBot@1`.
   - **SignalSenderNode** (`SignalSender@1`) — sends a Signal message (optional base64 attachment as a `data:` URI) through a signal-cli-rest-api bridge (`POST {apiUrl}/v2/send`). Outbound counterpart of `FromSignal@1`. **Number/ApiUrl resolution** is shared with the trigger via `SignalChannelEndpointResolver`: (1) the tenant's `System.Communication/SignalChannel` singleton — the communication controller ALWAYS projects it into every pipeline's GlobalConfiguration under the key `"signal-channel"` (contract doc: `AdapterService.AddSignalChannelConfigurationAsync` in octo-communication-controller-services), used ONLY while `RegistrationState == Registered (2)`, otherwise warned and treated as unconfigured; (2) the DEPRECATED legacy settingsConfiguration/numberAttribute/apiUrlAttribute mechanism plus the literal node properties (deprecation warning when it supplies the endpoint — existing pipeline definitions keep working, new-style ones omit all of it); (3) neither → the sender reports and stops, the trigger stays idle with one clear log line (no crash, no error-state loop). The reply/appUrl concern (`SignalAppUrl`) stays app-level and untouched.
