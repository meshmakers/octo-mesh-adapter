# Transform nodes

2. **Transform Nodes** (`src/MeshAdapter.Sdk/Nodes/Transform/`): Data processing nodes
   - **AllocateCommunityEnergyNode** (`AllocateCommunityEnergy@1`, AB#5634) — energy-community allocation per 15-min slot (dynamic key, as EDA does it). Loads consumers/producers, their `ParticipationPeriod`s, `PartitionFactor` and `MeteringDataSource`, plus the raw input anchors (`1-1:1.9.0 G.01` / `1-1:2.9.0 G.01`) and reads their rows from the archive (paged, ordered). Per slot: o_p = floor_q(pf_p·g_p) (`G.01T`), a_i = floor_q(pf_i·c_i) when demand fits, else floor_q(E·w_i/W) (`G.03`), surplus u_p (`P.01T`) by largest remainder; every register of a slot carries the WORST input quality of that slot (decision V-2, L1 < L2 < L3 — only the real quality ranks; a manual input counts with its real quality, manual entry is the row origin, not a quality (AB#5356); a missing value counts as `MissingQuality` L3; a legacy DataQuality key 4 is read as L3); the allocation rows are written as automated; all arithmetic in integer units of `Resolution` (0.001 kWh), so Σ(G.01T−P.01T) = ΣG.03 exactly (asserted). Days are cut in `TimeZone` (Europe/Vienna, 92/96/100 slots); `SourceDocumentDate` = reporting cut-off of D, so a re-run is bit-identical. A day with a participating metering point whose data source is not allocatable (missing attribute = Eda) is aborted (no records). Output records have the `ParseConsumptionRecord@1` shape and feed `SaveTimeRangeSeriesInArchive@1` unchanged; optional per-day summary (coverage, surplus ratio). Pure parts in `Nodes/Transform/CommunityAllocation/` (`CommunityAllocator`, `AllocationDayPlanner`). OBIS mapping configurable.
   - **CommunityEnergyBalanceNode** (`CommunityEnergyBalance@1`, AB#5639, BAL-01..03) — provisional community balance of the last N closed slots (`slots`/`slotsPath`, default 4, max 96; a slot is closed when `to <= now`, UTC grid of `SlotLength`), oldest first. Reuses the allocation's own parts — `CommunityMemberLoader` (members, participation, input anchors), `CommunityInputReader` (archive read), `CommunitySlotAllocation` (per-slot call into `CommunityAllocator`) — extracted unchanged from `AllocateCommunityEnergy@1`, so a slot with complete inputs equals the final run (pinned by `CommunityEnergyBalanceNodeTests.EverySlot_EqualsTheFinalAllocationOfTheSameInputs`). Missing values count 0; a participating non-allocatable (Eda) point gives `status: error`. Output `{status, message, generatedAt, provisional, simulatedIncluded, slots[{from,to,productionKwh,offeredKwh,allocatedKwh,surplusKwh,consumptionKwh,shortfallKwh,coverage,reported{expected,received,simulated},meteringPoints?}]}`; `meteringPointsPath` adds per-point registers. `simulatedIncluded` (BAL-02) is true only when at least one participating point is simulated and each of them has a value in a returned slot; with no simulated member it is false (AB#6645). Writes nothing.
   - **PrepareMeterReadingsNode** (`PrepareMeterReadings@1`, AB#5637, MTR-02..04) — validates self-reported readings (`readingsPath`, default `$.body.readings`) value by value: `UNKNOWN_METERING_POINT`, `NOT_SELF_REPORTED`, `OFF_GRID`, `DUPLICATE_SLOT` (every occurrence), `OUT_OF_RANGE`, `IN_FUTURE`, `NOT_PARTICIPATING`, `DAY_FROZEN` (cut-off via `AllocationDayPlanner`, `cutOffTimePath` as in the allocation). Accepted values become `AllocationEnergyData` records (raw register, quality `L1`, `CreationTime` = now) that `SaveTimeRangeSeriesInArchive@1` writes with the allocation pipeline's column block; result `{status ok|partial|error, message, accepted, rejected[{reading,value,code,message}], frozenUntil}`. Request-level errors (no values, more than `maxValues`) give `status: error`, `code: VALIDATION` and no records. Never logs the request.
   - **RegisterSelfReportedMeteringPointNode** (`RegisterSelfReportedMeteringPoint@1`, AB#5636, MTR-01) — registers a self-reported metering point with the entity chain of `create-demo-community.yaml`: customer (default one per tenant by well-known name, or one per customer name) → `EnergyCommunity/AssociatedFacilities` → own facility ← `System/ParentChild` metering point (`MeteringDataSource = 2`) ← raw anchor (`{mpRtId}_{obis}`) and participation period (`{mpRtId}_participation`, from local midnight of `participationFrom`). Validates fully before any read (`VALIDATION`, `NUMBER_RESERVED` outside `reservedNumberPrefix` AT009998), then lookup + write in ONE scoped transaction (`DIRECTION_CONFLICT`, `NOT_SELF_REPORTED` abort it). Idempotent: same number + direction returns `created: false`, the same rtIds, updates only the fields the request names, never the participation start. The customer is inserted in its own `ApplyChangesAsync` call so the engine's `AutoIncrementModifier` assigns `CustomerNumber` (it returns early for a batch that also contains types without an auto-increment attribute). **City parent (AB#6014 finding):** every facility gets exactly one `Basic/City` parent (`System/ParentChild`) — the EC app fails with "City data not found" without it. Optional request `zipcode` (int or digit string), else config `DefaultZipcode` (5020); lookup by `Basic/City.Zipcode` (Int), several matches ⇒ lowest rtId; no match ⇒ `CITY_NOT_FOUND` (default-zip message names Locations.Austria), resolved before the first write (even before the customer insert). Address `Zipcode`/`CityTown` come from the city. Re-register links a city to a facility WITHOUT parent (`Basic/TreeNode` outbound) and fills placeholder address fields; an existing parent is never changed.
   - **DataMappingNode** (`DataMapping@1`) — maps a value by a list of source→target entries. **The shape of `path` decides (AB#6589):** a path that addresses one value (indexes included) keeps the original single-value route exactly — one typed read, one write at `targetPath`. A multi-match path — wildcard `[*]`, recursive descent `..` or filter `[?(...)]`, detected with the same two-stage test the SDK uses for `GetArray<T>` (`IsMultiMatchPath`: a character pre-filter, then the public `JsonPathParser`) — maps **every addressed element in place** through `IDataContext.UpdateMatchesAsync`. In place only: `targetPath` is the same path or left out (its default `$` is what "left out" looks like), anything else is rejected before a byte is written (`DataMappingMultiMatchNeedsInPlaceTarget`, names node and both paths), and so is a non-default `targetValueWriteMode` / `targetValueKind` / `documentMode` (`DataMappingMultiMatchIgnoresWriteSetting`) — the in-place write does not use them and silently ignoring a configured setting (`IgnoreExisting` would mean "never map") is worse than refusing it; null elements are skipped, elements without a matching entry stay, a path that matches nothing is a warning and the chain continues, an element that cannot be read as `sourceValueType` fails the node naming its position (`DataMappingElementNotConvertible`), a Secret marker element is refused. 🔴 **The run is not atomic, by decision:** `UpdateMatchesAsync` writes each element back as its callback returns, so a failure midway leaves the earlier elements mapped (pinned by `ElementFailureMidway_FailsTheNode_AndLeavesTheEarlierElementsMapped_ByDesign`); the execution ends and its data is discarded. An all-or-nothing run would need a second read-and-stage pass over every match, about doubling the per-element cost and making the node slower than the `ForEach@1` it replaces — do not "fix" this without that trade-off. 🔴 **One conversion, shared:** the mapping entries go through `ConvertToConfiguredType` — the single method AB#2141 / AB#6074 will replace — wrapped in `MappingLookup`, which converts each entry lazily and at most once per run in configuration order, so what the single-value route did (an entry behind the first match is never converted, an unconvertible entry only fails when it is reached) stays true and a run over 123,000 elements does not convert the same entry 123,000 times. One debug line summarises a wildcard run instead of one per element. ⚠️ **Not a 10x tool:** the per-element cost is the data context's own multi-match write (one child context and one write-back per match); measured on 123,000 rows it is ~1.3x faster than `ForEach@1` + `DataMapping@1` per row (1.07 s against 1.43 s) and needs ~33 % less extra memory (+184 MB against +274 MB peak working set over the generation baseline). A larger gain needs a bulk operation on the data context in octo-communication-sdk. Tests: `DataMappingNodeTests` (single value, unchanged) and `DataMappingNodeWildcardTests` (real `DataContextImpl`).

   - **VerifyCaptchaNode** (`VerifyCaptcha@1`, AB#7251) - verifies a CAPTCHA token (provider `Turnstile`, siteverify endpoint fixed in code) with the tenant's own Secret attribute (`tenantSecret`, read as `Caller`/`ServiceAccount`) else the platform's `System.Communication/SecretDefault` named `defaultKey` (read with a system session, by well-known name, in the executing tenant only) and writes exactly `{ valid, source: tenant|default|none, reason: not-configured|invalid-token|verification-unavailable }`; Cloudflare's error codes are mapped, never passed on, and the plaintext never enters the data context.    - **MakeHttpRequestNode** (`MakeHttpRequest@1`) - Executes one HTTP request, or walks a paged endpoint, and stores the response at `TargetPath`. Four capabilities were added additively and each is **inert unless configured**, so a pipeline that sets none of them behaves byte for byte as before. **Configured access:** `ApiConfiguration` names a GlobalConfiguration entry supplying `baseUrl` and `apiKey` (`HttpApiSettings`, resolved through the same pattern as the SFTP nodes); the URL is then a path relative to that base and the key travels in `AuthHeaderName` (`Authorization` by default, scheme-less unless `AuthHeaderValuePrefix` supplies one), so the key never has to sit in the pipeline definition or in the data context. **A URL that names its own scheme is refused before any request goes out** when `ApiConfiguration` is set - the entry already decides the host, so a scheme in the URL is a contradiction the author should hear about rather than a request nobody meant. The test asks whether a scheme is spelled out (`HasExplicitScheme`), deliberately **not** `Uri.TryCreate(UriKind.Absolute)`: on Unix a leading slash makes that succeed with an implicit file scheme, so `/article` - the ordinary way to write a path - counts as absolute on a Linux agent and not on a Windows one, which is a green local suite and a red CI. **Paging:** `Paging.ItemsPath` names the array inside one response (single-level `$.name`); the walk appends the page and page-size parameters to whatever query the URL already carries and collects every page into one flat array written once, at the end, so a run that fails part way leaves no half-filled array. It stops on an empty page and, unless `StopOnShortPage` is off, on a short one; a response carrying no array at `ItemsPath` and reaching `MaxPages` both **fail** rather than truncating quietly - a target that ignores the page parameter would otherwise return the same page forever. **Retry and timeout:** `Retry` spends its attempts on the page that failed and never restarts pagination; transient means 5xx, 408, 429, network errors and timeouts, everything else fails at once. `TimeoutSeconds` applies per attempt through a `CancellationTokenSource` built on the node's `TimeProvider` - the shared `HttpClient`'s own timeout is process-wide and is never touched. **Failure semantics:** `OnHttpError` defaults to `LogAndStop`, which is what the node has always done - report and skip the following nodes while the execution still succeeds. The default deliberately stays that way: `MakeHttpRequest@1` is released and its consumers cannot be enumerated, so flipping it would turn other tenants' pipelines red on their next chart update (the house pattern for that is a new node version). `Throw` fails the execution instead, and it fails with a **typed** exception, never a raw cancellation - `ForEach@1` isolates every exception except `OperationCanceledException`, so a timeout escaping raw would abort a whole loop instead of failing one iteration; that is what makes per-item isolation with `continueOnError` work. Configuration mistakes (undefined or half-filled entry, a scheme-qualified URL with `ApiConfiguration`, paging without `ItemsPath`) **always** throw, whatever `OnHttpError` says - a mistyped entry that merely logged would leave an operator with a green execution that called nothing. Everything that is not an HTTP outcome - a response the storage step cannot handle, a header the target refuses - keeps the node's original report-and-stop net in **both** modes. **Guarded against the ways these could fail quietly:** the configured key is attached with `TryAddWithoutValidation`, because the strongly typed parsers reject perfectly good keys (a base64 key with '=' padding under the default `Authorization` header) and put the offending value into the exception message, which the node's own net would then log - so a validating add both lost the request and leaked the key. A header parameter of the same name as the auth header is refused as a configuration mistake, naming the header and never the value. The resolver checks that `baseUrl` is an absolute http/https URL, because a scheme-less base passes a blank check and only fails deep inside the send, where it is reported and swallowed. A computed backoff wait is **clamped** to 60 s while `MaxAttempts` above 10 is **rejected** - a wait can be honoured approximately, an attempt count cannot, and silently running fewer attempts than were asked for is the kind of thing an operator discovers during an incident. The same rule decides the rest of the preflight: `timeoutSeconds` must be positive and within what the timers accept (only leaving it out means "keep the client's own"), `paging.pageSize`/`maxPages` at least one and `firstPageNumber` not negative, `authHeaderName` a real HTTP token, and a URL carrying a fragment is refused while paging is on because a fragment never reaches the server and the page parameters behind it would be dropped from every request. Paging refuses `responseFormat: Base64`, `contentLengthTargetPath` and a URL that already carries one of the page parameters, each of which would otherwise be ignored or make every page identical until a page cap it never really reached. **A retry re-sends the request unchanged**, so on a non-idempotent method it can repeat a state change the target already applied - documented on the property rather than prevented, because which targets tolerate that is the pipeline author's call. The `LogAndStop` path logs the **full** response body, which is what the node reported before it could throw; only the thrown message is truncated. **Explicit nulls:** the new numbers and strings are nullable with constant defaults resolved where they are read, because the pipeline definition deserializer is YamlDotNet and a key that is present and null overwrites a property initializer (the `JsonNullAsDefaultAttribute` used by the settings records only covers the System.Text.Json path).
   - **RenderDelimitedTextNode** (`RenderDelimitedText@1`) - Renders an array of records into ONE delimited-text document at `TargetPath`: one row per array element, one column per `Columns` entry, joined with `Delimiter` and `LineEnding`. Write counterpart of `ImportFromCsv@1` - though not a round trip: that reader treats an unescaped `"` as the start of a quoted field, so a value containing one comes back split differently than it went out, and this node emits no quoting to signal it. What could not be composed from existing nodes is the last mile: `Concat@1` already builds a single delimited *line* from relative `ValuePath`s, but nothing joins an array of strings into one document. A column is a constant (`Value`), a read (`ValuePath`, relative to the record) or - with neither set - **empty**, which is how a fixed layout expresses a reserved field; such layouts are mostly reserved fields, so the empty entry is the common case rather than an oddity. Setting both is a configuration error. **`Required`** turns an empty rendered value into a failure naming record and column, checked on the rendered text so absent, null and empty are one rule instead of three; unset it is inert. **Value to text follows the house rule** the other text-producing nodes use (`Concat@1`, `FormatString@1` via `JsonStringifyHelper`, which is `internal` to the SDK and had to be reproduced rather than reused): a number emits its **raw JSON token** so `0.00` stays `0.00` and no culture can reshape it, a boolean emits `True`/`False`, absent and null emit nothing. An object or array at a `ValuePath` is **refused**, because the same house rule would serialise it as indented multi-line JSON and destroy the record structure far more quietly than a stray delimiter would. **There is no quoting**, deliberately: fixed-layout delimited formats generally have no escaping convention, so emitting quotes would hand them to the receiver as payload. A value carrying the delimiter, CR or LF is refused (`OnDelimiterInValue: Fail`, the default) or rewritten (`Replace` / `Strip`, both warned) - never passed through, since it shifts every following column and the receiving side cannot tell. Constants are checked identically, and a `Replacement` containing the delimiter or a line break is rejected in the preflight because it would only move the problem. **The delimiter is exactly one character**, which is not a simplification but the condition under which the guarantee holds at all: cleaning can compose a longer delimiter out of the characters it leaves behind (removing `ab` from `aabb` yields `ab`), and a per-value check cannot see one that forms across the join between two columns; the counterpart reader splits on the first character only, so a longer one would not round-trip either. **An empty input array writes an empty string and never skips the write** - load-bearing rather than tidy: a downstream `If@1` guarding the delivery compares against `""`, and with the path absent that comparison reads `null`, so "not empty" is TRUE and exactly the empty delivery the guard exists to stop goes out. A `Path` that is not an array fails instead, since a silently one-row document from a mis-typed path is worse than a loud error, and so does a **record that is not an object** - every read column would render empty while the constants print, which is structurally valid output with nothing in it. If the source ever reports records that the iteration does not yield, that fails too rather than writing an empty document over them. `LineEnding` is `Lf` or `CrLf` and never `Environment.NewLine`, so the same definition produces the same bytes on every host. Configuration mistakes - empty/null `Columns`, a null entry, a column setting both, an unusable `Delimiter` or `Replacement`, an undefined `LineEnding`/`OnDelimiterInValue`, a `Path`/`ValuePath` that does not parse or that selects a set (wildcard, filter, recursive descent - a column holds one value, and such a path can resolve against one backing store and render empty against another), and a blank `Path`/`TargetPath` - **always** throw before anything is written or the chain continues. The blank target path matters more than it looks: the data context reads an empty path as the document ROOT, so the rendered document would replace the entire pipeline data while the chain carried on. **Explicit nulls:** `LineEnding`, `TrailingNewLine`, `OnDelimiterInValue` and `Replacement` are nullable with constant defaults resolved where they are read, because the pipeline deserializer is YamlDotNet and a present-but-null key overwrites a property initializer (`JsonNullAsDefaultAttribute` covers only the System.Text.Json path).
   - **ConvertToCsvNode** (`ConvertToCsv@1`, AB#6733) - Turns an array of records into ONE real CSV document at `TargetPath`: header row, RFC 4180 quoting, a number and date format per column, optional UTF-8 BOM and base64 output (`ContentLengthTargetPath` gives the byte length) — the content `CreateFileSystemUpdate@1` stores as a file-system item, which `SendEMail@2` then attaches by its binary id (it cannot attach base64 directly). Generic - the grid-operator layout of the interim voestalpine delivery (AB#6403) is just configuration. Sibling of `RenderDelimitedText@1`, which stays: that one writes a fixed layout WITHOUT quoting on purpose, this one writes CSV. `Columns` unset takes every scalar property of the records in order of first appearance. A column is `ValuePath` (relative, single-valued) or a constant `Value` or empty, with `DataType` (`Auto`/`String`/`Number`/`Boolean`/`DateTime`), `Format` (.NET), `Culture` (node-level default, column override; unset or `""` = **invariant**, so a decimal point; `de-AT` gives a decimal comma and German day/month names; a string source value is always READ invariant; an unknown culture throws, which also covers an invariant-globalization host), `Decimals` (rounded half away from zero), `Factor` (applied before rounding), `TimeZone` (DateTime only) and `Required`. `Quoting`: `Minimal` (default) / `Text` (strings, dates, header; not numbers or booleans) / `All`. A number without `Format`/`Decimals`/`Factor` keeps its raw JSON token; a date without an offset is read as UTC (stream-data house rule). 🔴 The column property is `dataType`, **not `type`**: `type` inside a pipeline definition is taken by the serializer and never reaches the column (the deserialization test found it - a YAML `type: DateTime` was silently dropped). Defaults are nullable and resolved where read (YamlDotNet lets a present-null key overwrite an initializer). An empty array writes a header-only document with explicit columns and an empty string without; the write is never skipped. Configuration mistakes always throw before anything is written (blank paths, delimiter not exactly one char / line break / `"`, undefined enum, ambiguous or null column, `Format`/`Decimals`/`Factor`/`TimeZone` on a constant or a type they do not apply to, unknown time zone, set-selecting or unparsable value paths). Tests: `tests/MeshAdapter.Sdk.Tests/Nodes/Transforms/ConvertToCsvNodeTests.cs` (incl. the grid-operator layout byte for byte, the CET/CEST gap and repeated hour) and `ConvertToCsvConfigurationDeserializationTests.cs`.

   - **ImportFromCamt053Node** (`ImportFromCamt053@1`) — parses a camt.053.001.02 XML bank statement into an array of normalized booking objects (one per `Ntry`) written to `TargetPath`. **Namespace-agnostic** (resolves by local element name), so both the ISO standard namespace (`urn:iso:std:iso:20022:tech:xsd:camt.053.001.02`) and the Austrian STUZZA/APC variant (`ISO:camt.053.001.02:APC:STUZZA:payments:003`) are handled by the same node — a namespace-bound parser silently yields zero entries on the other dialect. Reads the base64 file from `$.files[FileIndex]` (FromHttpRequest upload). Emits per entry: composite `transactionId` (IBAN|AcctSvcrRef, else IBAN|LglSeqNb|position), signed `amount` (sign from CdtDbtInd), currency, booking/value dates, `direction` (0=Credit/1=Debit), direction-dependent counterpart name/iban/bic, concatenated `purpose` (Ustrd + structured CdtrRefInf/Ref), payment/E2E/mandate references, SEPA creditorId, `bankTransactionCode` (BkTxCd SubFmlyCd — ESCT/ESDD/CWDL/STDO/…), plus accountIban/lglSeqNb/position. Feeds the standard GetOrCreate→CreateUpdateInfo→ApplyChanges flow to create Basic.Accounting/BankTransaction (MatchState=Unreviewed). Parser core `ParseCamt053` is pure/static and unit-tested; the real-corpus regression test is gated on the `CAMT_CORPUS_DIR` env var (confidential data never enters VCS). Built for the accounting BelegCockpit camt import (AB epic Rechnungseingang/Bankabgleich).
   - **AnthropicAiQueryNode** (`AnthropicAiQuery@1`) — queries Claude, optionally with MCP tools loaded from `{mcpServerUrl}/{tenantId}/mcp`. **Shim over the shared engine:** the node only maps its configuration to `Internal/LlmQueryOptions` and supplies `Internal/AnthropicMessagesChatClient` — the Messages API as an `IChatClient` of Microsoft.Extensions.AI.Abstractions around the request body, cache breakpoints and error texts the node always sent, no Anthropic SDK. Everything described below runs in `Internal/LlmQueryEngine`: settings from AiConfiguration and prompt template, the prompt (`LlmPromptBuilder`), MCP (`LlmMcpSession`: token, handshake, tool list, tool calls), the tool loop, the answer (`LlmResponseProcessor`, `AiJsonSchemaResponseProcessor`) and the usage. The engine reads no node configuration type and knows no provider wire format, so another LLM query node needs only a mapping to `LlmQueryOptions` and a chat client. 🔴 **The wire of `AnthropicAiQuery@1` must not change by accident:** `AnthropicAiQueryNodeGoldenRequestTests` pins the requests of three pipeline shapes (document analysis; chat with MCP tools on the caller's identity; knowledge generation with schema, cached source and a repair call) byte for byte, headers and MCP handshake included; record again only for a deliberate wire change (`OCTO_UPDATE_GOLDEN_REQUESTS=1`) and review the diff of the files. Rules of the translation (assistant turns are replayed as delivered, tool results become `tool_result` blocks, the temperature is sent as its shortest decimal text): `AnthropicMessagesChatClientTests`; the engine against a scripted chat client: `LlmQueryEngineTests`. `LlmMcpSession` is deliberately not `McpToolClient`: the two differ on the wire (client name, no `notifications/initialized`, a failed handshake only loses the tools). Lifted from the LlmQuery prototype (Philipp Schwaab): an empty or malformed AiConfiguration payload ends in the node's own settings with a warning that shows nothing of the payload; conversation history accepts a content-parts array (text parts joined) and leaves out entries whose role or content is not text; a tool result over the cap (50 000 UTF-16 code units) is cut without splitting a surrogate pair; the tool-call log names the arguments, never their values. 🔴 **What a tool sends back is redacted before the model sees it:** tool results and tool error texts pass through the secret registry of the execution, so an MCP server that echoes the bearer in a tool result or an error cannot hand the token to the provider or, through the answer, to the data context (`LlmQueryEngineTests`). Not redacted: the tool names, descriptions and input schemas of `tools/list`, which go to the provider as the server declared them; a server that puts the bearer into a declaration exposes it. 🔴 **Three rules of the tool loop and the skip path, found in review and pinned by `LlmQueryEngineTests`:** a tool the model asks for is called only when it was offered to the model, so `mcpToolNames` holds for the calls and not only for the list (a refused call goes back to the model as an error result, with one warning); when `maxToolRounds` is spent, a further batch the model asks for is not run before the query fails; and when the node skips for missing content and hands on to the rest of the pipeline, a failure of a later node is that node's own (it used to be logged as an AI error and, with `continueOnError`, the rest of the pipeline ran a second time). 🔴 **No identity, no MCP call (AB#8685):** an MCP URL (node `mcpServerUrl` or, more often, the inherited `AiConfiguration.McpServerUrl`) without `mcpServiceAccountConfigName` or delegation to the caller is **skipped** — no network call, one warning per execution naming the node path and the missing setting, the query runs without tools (and the no-tools system-prompt suffix applies, without a second warning). Before, the node called MCP unauthenticated, got 401 from the auth-enforcing MCP service and lost its tools silently (~1,200 401s/month on prod-1). `HasMcpIdentity` decides; tests `AnthropicAiQueryNodeMcpIdentityTests` (unit) and `AnthropicAiQueryNodeMcpIdentityIntegrationTests` (real MCP SDK server). MCP auth normally uses a **service account** (`mcpServiceAccountConfigName` → `IServiceAccountTokenService.AcquireServiceAccountTokenAsync`, which RETURNS the token of exactly that account, cached per tenant + client + issuer). 🔴 **Never read the MCP token from `IServiceClientAccessToken` again (AB#8699):** that singleton is the adapter's own identity, shared by every pipeline of the process; reading back from it handed a node another account's token (two accounts in one adapter), the adapter's own token (after its refresh) or a foreign tenant's token. The node no longer has the holder as a dependency (test `TheNodeCannotReachTheAdaptersProcessWideTokenHolder`). 🔴 **Fail-closed when the configured account yields no token (AB#8699):** missing/broken `ServiceAccountConfiguration`, a refused token request or an exception end in ONE warning ("… did not yield an access token …; no MCP call is made and the query runs without tools") and no MCP call — the query still runs (the AB#4541 rule that a broken account never fails the pipeline stays), but the former unauthenticated MCP attempt is gone. Tests `AnthropicAiQueryNodeServiceAccountIsolationTests` (real token service, cases two accounts / adapter refresh / foreign tenant / fail-closed). **`mcpDelegateToCaller`** (AB#5031, default `false`) switches that identity: the node exchanges `IEtlContext.CallerAccessToken` for a delegated token via `AcquireDelegatedTokenAsync`, so the MCP server applies the **calling user's** roles and data permissions instead of the service account's full `octo_api` reach. 🔴 That mode is **fail-closed** — no caller token, no service-account config, or a failed acquisition all throw; neither degrade path applies, because continuing under another identity (or none) would defeat exactly the authorization the mode exists to enforce. Requires a trigger that carries a caller token (`FromHttpRequest@2`, not anonymous); channel assistants (Teams/Signal/e-mail) have no caller and must leave the flag off. Used by the accounting app's `/aiPrompt` Q&A pipeline. 🔴 **Every token the node holds is a registered secret of the execution:** the service account's token, the delegated token and the caller's own access token it is exchanged for are passed to `INodeContext.RegisterSecret` right after they are read or acquired and before any log line, MCP call or token exchange, so an MCP server that echoes the bearer in a 401 body, or an identity service whose refusal quotes the subject token, shows `***` in the execution log, the error of the execution, debug snapshots and the result. The subscription's preferences are read in the same system session as the configuration. Rules live in the pure `NotificationDigest`: a watermark, not a set diff. `ProcessedUntil` is the latest change the engine has handled; `SentRows` (records `RowRtId` / `SentAt` / `ChangedAt`) is what the user got. A new row is a row changed after `ProcessedUntil` − 5 min that is not in `SentRows`, so a row created or changed days later still counts, and a row the user already got is not sent again within 30 days, even when it changes (`SentRowRetention`). Pruning (`Prune` / `Remember`) never drops a row the overlap can still read; the rest is kept 30 days, newest first. `SentRows` holds at most 10 000 rows (`MaxSentRows`), the rows the overlap can read again included: when a flood (an import, a replay, a fix-up script) puts more than that into the overlap, the oldest change times are dropped and `ProcessedUntil` moves to the newest dropped change time plus the overlap (`PastOverflow`), so no dropped row is read again. The price is the overlap's protection for those rows: a write stamped before the cut but committed after the run is not mailed. The cut is never made at or after the change time of the last row read, because rows of that same millisecond may still be unread; so more than 10 000 rows that changed in one millisecond are all kept. Start = the later of the preference's creation and the subscription's `DeployedAt`; a run is a new start (`Plan`) when there was no run yet, for Onwards when there was no run since the start (a redeploy), when the query, the user or the start option changed, or an Onwards state has no `ProcessedUntil`. An Onwards start (`SkipExistingRows`) reads from the moment that caused it: the start for a first run or a redeploy, the preference's `RtChangedDateTime` when the recipient or the start option changed, and for another query the later of the subscription's `RtChangedDateTime` and the state's `LastRunAt` (an update that touches only the association does not move the subscription's change time, any attribute write does, and the Studio always sends the attributes). `Plan` sets `ProcessedUntil` to that moment plus the overlap, so every row changed after it is new and is mailed by the same run, and a run that finds nothing keeps reading from there. The moment is fixed, not the time of the run, so a run that comes late (a lost immediate tick, an engine that was down) still mails what changed in between; the previous design recorded the latest change of the result at the run and lost those rows. A row that existed before the start is mailed as soon as it changes; recording the pre-start rows as sent instead (the first design) hid such a change for 30 days. `ProcessedUntil` may lie up to 5 minutes ahead until a later change passes it; a Catch up start reads from the beginning and mails everything not in `SentRows`. A redeploy is not a new start for Catch up: it reads on from its watermark, so the rows that changed during the pause are mailed and the older ones are not mailed again (the old rule read from the beginning and re-sent every row whose `SentRows` entry had expired). A run that saw no state and loses the insert to another run that created it meanwhile skips the tick instead of recording a false failure. Another user forgets `SentRows` and clears `LastSentAt` on its first write; a switch from Onwards to Catch up forgets them too, so it gives one full summary that may repeat rows (accepted 2026-10-15); Catch up to Onwards keeps them. The state also records `QueryRtId`, the query its rows came from: when the subscription points at another query, the run is a new start (the `QueryRtId` term of `NotificationDigest.Plan`), whoever changed the query - so an Onwards recipient never gets a whole new result as "new rows". A state without it (written before) keeps its last run and gets it on the next write. Nothing new writes the state itself and stops. Otherwise it renders through `NotificationPlaceholderResolver` — subject knows `${count}` only, the body is ONE row (`${column}` = query column, case-insensitive) repeated per row, at most 100 rows plus "...and N more", values escaped unless the template renders Plain (decided by `EMailSenderNode2.ResolveBodyFormat`): the five HTML characters as `EncodeForMarkup` does, and the Markdown control characters (`` \ ` * _ [ ] ( ) ! # | ~ ^ $ { } + ``) as numeric entities, so a row value from an import cannot become a link, an image or emphasis when `SendEMail@2` runs the body through Markdig; entities rather than backslashes because the text/plain half is the HTML-decoded body and shows the value unchanged. In Filter mode a column filters through the association, so a row would appear in the result when its associated entity changes, which the engine cannot notice; before this rule the first read counted such a row as new and the mail read dropped it, so a mail listed fewer rows than its subject said (or none) and the missing rows were recorded as sent for 30 days. This is a contract, not a fallback: there is no second mode that re-reads the whole result. 🔴 **The query reads as the pipeline's identity, never as the recipient** (decision 2026-10-12): one result serves every preference of the subscription, so per-recipient data permissions cannot apply. Every recipient gets the same rows, whatever data permissions they have in the Studio: who receives what is decided by whoever configures the subscription (`CommunicationManagement`), the same rule as every other background send in this adapter (`SendEMail@1`, `SftpUpload@1`, AB#5045). A type-level block on enforced data policies was built and dropped the same day: no other send in the stack does it, it blocked legitimate subscriptions, and it never looked at the recipient. Per-recipient reads need the recipient's effective roles, which identity serves only behind UserManagement (`users/{id}/roles`); a narrow endpoint there is the way forward when a tenant needs it. A "nothing new" run writes nothing unless the rows changed, an old error has to be cleared, or `LastRunAt` is more than an hour old — an idle tick is reads only. Routine lines (tick received, nothing new, still running, backing off, removed) log at Debug; the first run, a send and errors stay at Info and above. Two runs of one preference are kept apart by the in-process guard in `FromNotificationSchedule@1` and, across processes, by an atomic lease (`NotificationDeliveryStateStore.TryAcquireLeaseAsync`): `RunningSince` is written with a conditional update that applies only while it is empty or older than the lease expiry, and the run then re-reads the state and continues only when the stored lease is its own (millisecond precision); a write conflict counts as lost when another run holds the lease. The decision was made on the state read before the lease, so a run whose re-read shows another `LastRunAt` (another run finished in between, possibly with a mail) releases the lease and skips the tick instead of mailing from its stale `SentRows`. Every later write is fenced by the same field (`NotificationDeliveryStateStore.Unleased` / `HeldBy`, the engine's `AttributeNewerThanGuard`): a write made without the lease (idle write, a failure before the lease) applies only while no run holds a live lease and never touches `RunningSince`; the commit and a failure after the lease go through `SaveHeldAsync`: they re-read the state, write only when `runningSince` is still exactly the run's own lease (`PreparedNotification.lease`), and the write itself applies only while it is at most that lease; they are the only writes that release it (`ReleaseLease`). The re-read is there because the guard passes on an empty `runningSince`, so a run that took over and already released would otherwise be overwritten; the engine has no equality guard, so between the re-read and the write that run would need a whole send cycle. A run that outlived its lease therefore cannot clear the lease or overwrite the state of the run that took it over; its skipped commit means that run may mail the same rows again, and the commit logs a warning instead of "sent" (`RecordedSendAtAsync` re-reads `LastSentAt`, because the engine does not report a skipped guarded write). The first write of a state uses an rtId derived from the preference's (`StateRtIdFor`, bytes XOR 0x5A), so two runs that both saw no state cannot create two: the second insert fails on the duplicate key, a lease attempt then loses and a plain save updates the existing state instead. Not the preference's own rtId: the engine resolves an association target by rtId alone, which made `DeliveryStatePreference` point at the state itself. Tests: `IntegrationTests/Nodes/Notifications/NotificationLeaseIntegrationTests.cs` (stale reads and truly parallel attempts). Any failure of the node or of the nodes after it (send included) writes `LastError` and releases the lease; `ProcessedUntil` and `SentRows` stay untouched unless `sent` is true, i.e. the mail went out and only `CommitNotificationState@1` failed — then the catch records the rows too, so the same rows are not mailed again on every tick. That bookkeeping write is itself guarded: when it fails it is logged and the original error is rethrown. In a dry run nothing is written (no lease, no state) and the mail is still rendered for `SendEMail@2`'s intent.    - **CreateUpdateInfoNode `recordArrayItemUpdates`** (`CreateUpdateInfo@1`, AB#7442, engine part AB#7445) — emits an `EntityUpdateInfo` that carries atomic RecordArray item updates (`EntityUpdateInfo.CreateRecordArrayItemUpdate`): per entry `attributeName` (the RecordArray), `matchAttributeName` + `matchValue`/`matchValuePath`, `attributeUpdates` (`valuePath`/`value`, `=now()` as ISO-8601 text); optional `updatesPath` iterates an array (match/value paths relative to the element, like `UpdateRecordArrayItem@2`). **No read of the entity**: `ApplyChanges@2` hands the info to the engine, which writes the named members of the matched record in ONE atomic MongoDB update (`$set` + `arrayFilters`, see engine/engine-mongodb `CLAUDE.md`), so parallel executions changing different records of one entity never lose each other (same record: last write wins) — the cure for the lost updates of the read-modify-write pattern (`GetRtEntitiesByType` → `UpdateRecordArrayItem` → whole array → `CreateUpdateInfo`), which stays known-unsafe. `UpdateKind: UPDATE` only; may be combined with `attributeUpdates` for other attributes (same statement), a whole-value update of the same RecordArray is refused by the engine. An empty match value skips that entry with a node warning; a record that matches nothing is skipped and `ApplyChanges@2` logs the engine's warning (message 27, nothing written, no version bump; partial misses of a multi-entry update are silent). `ApplyChanges@2` keeps all item updates when it merges several infos of one entity (in order, last value wins per record member); the dry-run intent reports `recordArrayItemUpdateCount`. Engine validation refuses unknown attribute/member, wrong value type, the match member as target and every `Secret` member. The info travels through the data context as System.Text.Json (ISO-8601 text becomes `DateTime`; the engine renders it back as text for a String member).
