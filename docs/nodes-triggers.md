# Trigger nodes

4. **Trigger Nodes** (`src/MeshAdapter.Sdk/Nodes/Trigger/`): Pipeline initiation nodes
   - FromHttpRequestNode/FromHttpRequestNode2 (version 1 is deprecated; version 2 rejects callers without a valid access token unless `AllowAnonymous` is set, from another tenant, and without one of `RequiredRoles` when configured). Neither version lets the caller's `Authorization`/`Proxy-Authorization`/`Cookie` headers into `input["headers"]`: that is governed by the separate `ReceivesCredentialHeaders` flag on the route, **not** by `AllowAnonymous`. Conflating the two was a defect — apps attach the operator's token per host, not per route, so an anonymous route receives tokens it never asked for, and the data root is echoed back in the response, persistable by `SetPipelineExecutionResult@1` and visible in the Studio debug panel.
     **Caller side channel.** `HttpRequestService` hands the trigger's execute delegate a `TriggerCallerContext(Principal, RawAccessToken)` instead of a bare `VerifiedPrincipal`; `FromHttpRequest@2` puts the raw token on `ExecutePipelineOptions.CallerAccessToken`, which `MeshContextCreatorService` forwards to `MeshEtlContext.CallerAccessToken`. That is the ONLY route the caller's credential travels: 🔴 it must never reach `input`/the data root (echoed + persistable — the `CredentialHeaders` filter is unchanged and independent), never `VerifiedPrincipal` (projected into that same data root) and never `IEtlContext.Properties` (that dictionary hangs on the `PipelineRegistration` and is shared across **all runs**, so a token left there would outlive its request). Only a `Bearer` scheme is accepted; `FromHttpRequest@1` and `FromTeamsBot@1` discard the context.
   - FromWatchRtEntityNode
   - FromExecutePipelineCommandNode (octo-communication-sdk; its command consumer is exclusive by design, so the tests fake the `RegisterCommandConsumer(name, handler, CommandConsumerOptions)` overload)
   - **FromSendNotificationNode** — command consumer **exclusive by design** (`ExclusiveByDesignReason` next to the registration): one endpoint per data flow that receives the *published* `SendNotificationsRequest` through the classic queue's message-type binding; exclusive by design keeps that binding and logs no deprecation warning. Details: `docs/developer-guide.md` "FromSendNotificationNode"; listed in the audit table of the `octo-distributedEventHub` repository. **Tenant guard:** the handler drops requests whose `TenantId` differs (OrdinalIgnoreCase) from the pipeline tenant — no pipeline start, no response, message acked, WARN with the two tenant ids only (no payload). The type-exchange fan-out itself (every tenant's queue still receives every request) remains until the tenant-routed exchange exists.
   - **FromNotificationScheduleNode** (`FromNotificationSchedule@1`) — one execution per schedule tick of a notification preference, started with `{ tenantId, preferenceRtId }` and recorded as `TriggerType = Scheduled`, like the cron trigger. The communication controller owns the schedule (`NotificationScheduleService`: one recurring `NotificationScheduleTick` per preference of a deployed subscription, in the preference's time zone) and sends to `queue:{QueueNames.NotificationScheduleChannelName}-{tenant}-{pipelineRtId}` lower-cased; the node listens on the same address without the `queue:` prefix, so the engine pipeline's rtId is part of the contract (`FromNotificationScheduleNodeTests` pins it). Consumer runs are parallel (MassTransit defaults), which is why `PrepareNotification@1` takes a lease.
   - **FromEmailNode** (`FromEmail@1`) — IMAP folder polling via MailKit. `Folder` is passed to `GetFolderAsync` **verbatim**, so it must use the SERVER's hierarchy separator — Dovecot/ssl-net uses `.`, and a mailbox may carry a real `INBOX` below `INBOX` (`INBOX.INBOX.Finanzen.Rechnungen`); a `/`-spelled path fails with `FolderNotFoundException`, so discover the name with an IMAP `LIST` rather than guessing. **Bounded by construction:** every message is downloaded in full and its attachments are base64-encoded into the batch, so the search result must never be consumed whole — `onlyUnread: false` over a mailbox with history (1697 mails in production) was an `OutOfMemoryException` 32 s after start, re-attempted identically on every restart, so the import never progressed. `ApplyBatchCap` limits one pass to `MaxMessagesPerPoll` (default 25) and lets a backlog drain over consecutive polls; `<= 0` restores the unbounded behaviour deliberately. **Scoped server-side:** `BuildSearchQuery` ANDs an optional IMAP `SINCE` onto the read-state predicate from `SinceDate` (absolute, wins) or `SinceDaysBack` (relative), so everything outside the window is discarded by the server. `SINCE` has date granularity and an INCLUSIVE lower bound, so a period starting `2026-01-01` keeps that day's mail. Without either the two reachable settings are "unread only" — which finds nothing once everything is flagged read — and "everything"; neither can express an accounting period. **An EMPTY window fetches nothing.** `windowOpen` / `windowOpenAttribute` is a separate value from the cut-off, because an absent cut-off cannot express "import nothing": it means "no date filter", and with `onlyUnread` switched off that is exactly the unbounded `SearchQuery.All` of an earlier incident. `ResolveWindowOpen` reads **unset as OPEN** (YamlDotNet lets a present-but-null key overwrite a non-nullable initializer, and `false` there would switch the deployed fleet off), and a closed window skips the whole polling pass before the connection and before the search, logging once per closed stretch. 🔴 Deliberately NOT the operator's `System/Enabled`: that switch belongs to whoever configures the channel, and flipping it from a computation needs a DATA FLOW deploy to take effect — which restarts every sibling trigger — whereas this value rides on the settings configuration and a single-pipeline `DeployPipeline@1` delivers it. The accounting channel derives both values from the OPEN fiscal years (`MIN(StartDate) WHERE IsClosed = false`), so "no fiscal year is open" closes the window instead of widening it to everything. **A declared attachment type is corrected from the content** via the shared `AttachmentContentType.NormalizePdf`, after the part is decoded so the `%PDF-` sniff also rescues an attachment MimeKit named `unknown`. **The mailbox is written back only after a CONFIRMED import:** `ResolveFlagDecision` takes the `\Seen` / `\Deleted` decision AFTER the run, and only when the pipeline said it imported the batch. 🔴 **"`ExecuteAsync` returned" is not that statement.** A pipeline ends perfectly normally while a node reported an error and stopped its branch — `MakeHttpRequest@1`'s `OnHttpError: LogAndStop`, its *default*, is documented as "report the failure and stop this branch, **leaving the execution successful**" — and the platform hands a trigger nothing finer: `INodeContext.Error` only writes to the pipeline log, `IEtlContext` carries no error state (and its `Properties` are shared across runs), and `PipelineExecutionStatus` is `Completed` for everything that did not throw. The ONE per-run channel back to the trigger is the value `ExecuteAsync` returns, which is the pipeline's **data root** (`EtlDataOrchestrator` ends on `dataContext.Get<JsonNode>("$")`). So the pipeline states the outcome itself: `successPath` names a plain dotted path in that root (optional `$.` prefix; indexes/wildcards/filters are rejected in `StartAsync`, since a confirmation matching a set has no single truth value) and **only the boolean `true` confirms** — absent, null, `false`, the string `"true"` and a number all read as unconfirmed, every one of them failing towards leaving the mail alone. Write the flag as the LAST node of the import branch (`SetPrimitiveValue@1 targetPath: $.importCompleted, value: true, valueType: Boolean`), where a branch that stopped early never reaches it. **Three levels, and only the first is unconditional** (`IsWriteBackAllowed`): a run that **threw** never flags — whatever is configured, and that is the actual fix (the gate sits behind the `await`, so an exception skips the assignment); `successPath` **unset** ⇒ a run that came back flags **as it always did**; `successPath` **set** ⇒ only a confirmed run flags. ⚠️ The relaxed default is deliberate: the strict one would stop every deployed `FromEmail@1` from marking anything read and re-offer its whole `SINCE` window on every adapter restart — a certain fleet-wide regression traded for one edge case. The node warns once per process that it cannot tell an import from a stopped branch and names the setting. A batch the `callerBinding` rejected also writes nothing, since it was never handed to the pipeline. **The success path built on exactly that hook** and closed the edge case level 2 leaves open: `successPath` now carries a BUSINESS success criterion — "at least one inbox item was created" — and it gates one of three post-processing modes shared with the Graph channel (`MailPostProcessingMode`): **A `MoveToFolders`** (confirmed ⇒ `doneFolder`, unconfirmed ⇒ `failedFolder`, leaf created, `/`-separated path walked from the personal namespace when the verbatim name does not exist), **B `Delete`** and **C `MarkAsRead`**. ⚠️ **An unset mode is DERIVED, never defaulted** (`ResolveEffectivePostProcessingMode`): a done/failed folder ⇒ A, else `deleteAfterProcessing` ⇒ B, else `markAsRead` ⇒ C, **else the trigger START FAILS** (see the `MailPostProcessingMode` entry below; there is no fourth mode) — and `ResolveFlagDecision` keeps reading the two legacy flags INDEPENDENTLY while no mode is named, so the combination "mark read AND delete" still produces one write carrying both. The mode is resolved in `StartAsync` **unconditionally** (it used to be evaluated only inside the log branch, i.e. only for a pipeline naming a `settingsConfiguration`), so a configuration that cannot work is heard on deploy instead of polling a mailbox it never changes. A run the `successPath` did not confirm sets no flags and expunges nothing; under `MoveToFolders` its batch still moves to the failed folder when one is configured. That branch is the migration: every deployed pipeline keeps behaving exactly as it did, and the same is true of `successPath` itself, which is still unset ⇒ "a run that came back counts". The runtime settings also moved OFF the definition: `settingsConfiguration` + the `*Attribute` names read interval, `onlyUnread`, mode, the three folders, batch cap, `SINCE` cut-offs, sender/subject filters and `successPath` out of a configuration entity, resolved **per poll** by `ResolveEffectiveConfiguration`. 🔴 The rule that forced it: **setting a setting must never rewrite a pipeline definition** — the definition is release content, and the accounting app's regex patcher moved one tenant's pipeline entity from v35 to v39 with nothing but a checkbox, edits a blueprint re-apply would then have thrown away. ⚠️ **`IGlobalConfiguration` is a per-registration SNAPSHOT** (`PipelineRegistryService` builds it once from the `PipelineConfigurationDto`), so a settings change reaches a running trigger only through a DataFlow (re)deploy, which stops and restarts it — the per-poll resolution is therefore correctness for the day that changes, not a live channel today. This used to happen per message inside the fetch loop, before the pipeline was even invoked: under the default `onlyUnread: true` the next poll asks for `NOT SEEN`, so a mail flagged ahead of a failing run was never offered again — silent receipt loss on a bookkeeping input channel, with nothing missing that anyone would notice (a production incident, where the throw happened in `SendEMail@1` *after* staging and was harmless by luck). ⚠️ Two properties this deliberately keeps: **the UID is still marked examined (`processedUids`) before the sender/subject filters**, because those `continue` past the bookkeeping and a rejected message would otherwise occupy the `MaxMessagesPerPoll` budget on every pass and starve the backlog behind it; and **a failed batch is not retried within the process lifetime** — `processedUids` holds it, which is what keeps a permanently failing mail from being re-downloaded and re-run every polling interval. That set is process-local, so a **restart** offers the mail again, unread and unflagged. Flags are applied in ONE `AddFlagsAsync` over the batch's UIDs, and the expunge is part of the same decision — `\Deleted` alone only marks. **The receive time never reads year 1:** `ResolveReceivedAt` prefers the `Date:` header, falls back to the server's IMAP `INTERNALDATE` (fetched for the whole batch in one `FetchAsync` before the messages are downloaded) and yields **null** when neither is usable — MimeKit reports both a missing and an unparsable `Date:` as `DateTimeOffset.MinValue`, and writing that through produced `UploadedDocument.SourceReceivedAt = 0001-01-01T00:00:00Z`, which sorts to the front of the accounting inbox and falls outside every fiscal year (67 mails from one sender in production emit no `Date:` header at all). `EmailData.Date` is therefore `DateTime?`: a null is *unknown*, and every consumer reads it via JSONPath into `CreateUpdateInfo@1`, which writes a JSON null as a null attribute value and skips an unmatched path. Both sources are read as wall-clock (`DateTimeOffset.DateTime`, offset dropped) because that is what the header path always emitted — converting to UTC here would shift every existing timestamp. **Status line after every poll:** the trigger reports one line through `ITriggerContext.ReportStatusAsync` — built by the shared `MailPollStatusLine` (see below) from what the trigger itself can count (`seen` = the batch it examined, `imported`/`failed` = the batch as a whole, since one execution serves the batch, `skipped` = client-side sender/subject filter and a rejected caller binding, plus the backlog the cap left) — and from the poll loop's catch an `ERROR …` line with the exception text; a closed import window reports an info line instead of a stale one. The line lands on the pipeline's `StatusMessage`, which the accounting app's import cards render with its age.
   - **FromSignalNode** (`FromSignal@1`) — polls a signal-cli-rest-api bridge (`GET {apiUrl}/v1/receive/{number}`) and fires the pipeline with a batch of normalized messages incl. downloaded attachment bytes (same `AttachmentData` shape as `FromEmail@1`). Number/ApiUrl resolution as described — see `SignalSender@1` above for the shared three-step order (registered `SignalChannel` singleton → deprecated legacy settings → idle); with nothing configured the trigger does NOT throw, it logs one clear line and stays idle, so a tenant without an activated Signal number never ends up in a deploy-error loop. **Status line, throttled:** reports `{UTC} · {number} · received N, processed N, rejected N` (received = data messages, receipts/typing excluded; rejected = sender filter + rejected caller binding) and `ERROR {UTC} · {number} · {exception}` with `isError: true` from the poll loop's catch — but through `TriggerStatusThrottle`, never per poll (default interval 5 s, each report is a write on the pipeline entity): on a success↔error transition, after a poll that received something, otherwise as heartbeat every `statusHeartbeatSeconds` (default 300, `<= 0` ⇒ default); a bridge that stays down repeats at most once per heartbeat. ⚠️ The loop's `OperationCanceledException` branch only ends polling on a STOP request now — an HttpClient timeout is a `TaskCanceledException` too and used to end the trigger silently for good.
   - FromMicrosoftGraphNode (Teams channel polling via Microsoft Graph)
   - **FromTeamsBotNode** (`FromTeamsBot@1`) — hosts the Bot Framework messaging endpoint `POST /{tenant}/teamsBot` (via `IHttpRequestService`), parses the inbound Teams activity, downloads file attachments (1:1 `application/vnd.microsoft.teams.file.download.info` via pre-authenticated URL; channel `reference` via Microsoft Graph SharePoint share), and emits the `EmailData`/`AttachmentData` shape at `$.Emails` plus conversation routing at `$.Conversation` (serviceUrl/conversationId/activityId/from) for `TeamsBotReply@1`. Credentials read from `MicrosoftGraphConfiguration`. Inbound JWT check via `ValidateInboundToken` (default `true`: signature against the Bot Framework signing keys, issuer, audience, lifetime — `TeamsBotTokenValidator`). Requires `HttpRequestService` to surface request headers (`input["headers"]`) **and** is the only trigger registering with `receivesCredentialHeaders: true`, because a Bot Framework token cannot be validated by the platform gate and the node has to read the raw `Authorization` header itself. **Status line:** `{UTC} · {route} · last activity handled, N attachment(s)` per processed activity (`last activity not processed (caller not bound)` for a rejected caller binding — the channel works, so not an error), and `ERROR {UTC} · {route} · …` with `isError: true` from the handler's catch and for a rejected inbound token (`inbound activity rejected: {reason}`, fixed validator texts, never token contents) — throttled by `TriggerStatusThrottle` to one report per 30 s (`StatusInterval`) except on a success↔error transition, because the route is public and a stream of bad tokens must not become a stream of writes. ⚠️ A push trigger reports only when traffic arrives: the line's age is *time since the last activity*, NOT a health check — real health would need a periodic bot-registration/credential probe (follow-up, not built).
   - **FromMicrosoftGraphEmailNode** — Polls an Office 365 mailbox FOLDER (path like `Archive/Invoices/ToDo`, '/'-separated, resolved from the mailbox root — never the inbox unless configured; a slash INSIDE a folder name is written `\/` and a backslash `\\`, e.g. `Inbox/02_Steuern \/ Finanzen` — resolved by `MailFolderPathSyntax.SplitGraphPath`, the ONE rule shared with `ListMailFolders@1`; same escapes for the done/failed paths, and the "available folders" hint of a failed resolution prints each name as a ready-to-paste segment via `EscapeGraphSegment`; a path without `\/` or `\\` resolves exactly as the historical `Split('/')` did) via Microsoft Graph client credentials. Executes the pipeline ONCE PER MESSAGE (batch of one `EmailData`) so success maps 1:1 to the per-message action: on success the mail is moved to `moveToFolderPathOnSuccess` (leaf folder auto-created); on failure it stays in the source folder and is retried up to `maxAttemptsPerMessage` times. **The attempt count is persisted ON the message as an Outlook category marker (`OctoMesh-Import-Attempt-N`), stamped BEFORE each run and cleared on success against the message's current categories** — so it survives adapter restarts and counts runs that killed the process (an OOM in a downstream node never reaches any failure handler, which an in-memory counter cannot survive). A message that exhausted its attempts is moved to the optional `moveToFolderPathOnFailure` (leaf auto-created), or skipped with a one-time warning when unset. A mailbox where the category PATCH fails degrades to in-process counting (warned, never blocks the import). Only `fileAttachment` contents are downloaded (item/reference attachments skipped). Requires Graph application permission `Mail.ReadWrite`. **Status line after every poll:** one line per poll through `ITriggerContext.ReportStatusAsync`, built by the shared `MailPollStatusLine` — `seen` = fetched from the source folder, `imported` = runs that confirmed (or completed, without a `successPath`), `failed` = handed to the pipeline but threw or did not confirm, `skipped` = sender filter, rejected caller binding, exhausted/parked — and from the poll loop's catch an `ERROR …` line carrying the exception text verbatim, which for a folder that does not exist lists the folders that do. The sender allowlist runs inside the pipeline, so "rejected by the allowlist" is deliberately NOT a count the trigger claims to know.
     **Success is what the PIPELINE says, not what did not throw.** `successPath` — the same contract `FromEmail@1` has carried since the success path was introduced, evaluated by the shared `MailSuccessPath` — names a plain dotted path in the returned data root, and only the boolean `true` confirms. An unconfirmed run is treated exactly like a failed one: the attempt is counted and the message stays in the source folder, so the parking machinery decides what happens once the budget is spent. Before this, done-or-failed was decided on "`ExecuteAsync` did not throw", and a mail whose import branch stopped on a reported node error was filed under Done with nothing in the inbox to show for it. ⚠️ `successPath` **unset** keeps the old behaviour exactly, so no deployed pipeline changes.
     **Three post-processing modes, shared with the IMAP channel** (`MailPostProcessingMode`): **A `MoveToFolders`** (what this node always did), **B `Delete`** (Graph's `DELETE /messages`, a soft delete into Deleted Items) and **C `MarkAsRead`** (`isRead` patch). An unset mode is DERIVED — a configured done or failure folder ⇒ A — and **with no folder at all the trigger START FAILS** (the former `None` fall-through left the message in the source folder, which re-reads the same capped batch for ever; no live M365 channel sits there, since the settings page refuses to activate one without mailbox, source and done folder). Resolved in `StartAsync` before the poll loop exists, and `ApplyPostProcessingAsync` has no "do nothing" branch left — its `default` throws, reachable only from a cast. 🔴 **The attempt parking is GRAPH-ONLY and stays that way**: it needs a per-message marker the mailbox persists across a process death, which an Outlook category is and IMAP has no portable counterpart for; under modes B and C attempts are still counted but there is nowhere to park, so an exhausted message is skipped. The IMAP channel's mode A therefore moves a batch aside on its first unconfirmed run.
     **Runtime settings live in a configuration entity, resolved PER POLL** (`ResolveEffectiveConfiguration`, shared readers in `ConfigurationSettingsReader`): mailbox, the three folders, interval, mode, batch cap, sender filter and `successPath`. Cached folder ids are dropped when the path behind them changes. ⚠️ `IGlobalConfiguration` is a per-registration snapshot, so a changed setting still needs a DataFlow (re)deploy to reach the adapter — see the `FromEmail@1` entry.
     **Sender authenticity — `Authentication-Results`.** `IncludeInternetMessageHeaders` (default off, inert when off) adds `internetMessageHeaders` to the `$select` and surfaces the headers named in `InternetMessageHeaderNames` (default `Authentication-Results`, `Authentication-Results-Original`, `ARC-Authentication-Results`, `Received-SPF`) on `EmailData.Headers`, plus the parsed SPF/DKIM/DMARC/compauth verdicts on `EmailData.Authentication`. The header was not empty before — Graph returns `internetMessageHeaders` **only** when it is selected explicitly, so it was never fetched; that one word in the `$select` is the whole feature. It stays opt-in because selecting it drags the full Received chain and the DKIM signatures onto every message, and only the named headers are surfaced because they land in the data context (echoed into every debug view, persisted by `SetPipelineExecutionResult@1`). 🔴 **Gate on DMARC, not on SPF.** SPF authenticates the envelope sender and DKIM the signing domain; neither has to match the `From:` the pipeline reads. Only `dmarc=pass` requires that alignment, so `spf=pass` alone accepts a mail whose envelope sender is the attacker's own (perfectly SPF-valid) domain while `From:` claims the vendor's — `EmailAuthenticationResults.IsDmarcPass` is the one verdict a rule may be built on. 🔴 **Only the FIRST occurrence of each header is kept.** A sender can put an `Authentication-Results` header into the message they submit and the receiving server *prepends* its own rather than replacing it, so only the topmost was written by infrastructure we trust; joining the occurrences would put a forged `dmarc=pass` into the same string as the real `dmarc=fail`, where any downstream substring or `MatchRegEx` check finds it. The occurrence count is reported as `HeaderCount` and anything above 1 makes `IsDmarcPass` false. A **null** `Authentication` means *nothing is known* (an internally generated mail carries no such header), never "authentication failed" — which way an unknown verdict falls is tenant policy, not the trigger's call. Result keywords are lower-cased because `MatchRegEx` is case sensitive; an absent method stays `null` rather than becoming `none`, so "never checked" stays distinguishable from "checked, no policy". The parser (`AuthenticationResultsParser`, RFC 8601) is pure/static and strips RFC 5322 comments from the **whole** value before splitting — Exchange writes `(client-ip=1.2.3.4; helo=mail.example)`, and splitting first tears the entry in two and reads the comment's own `key=value` pairs as method results.
#### Shared node helpers

- **`MailSuccessPath` / `MailRunConfirmation`** (`Nodes/Trigger/MailRunConfirmation.cs`) — the ONE per-run channel from a pipeline back to the mail trigger that started it, shared by `FromEmail@1` and `FromMicrosoftGraphEmail@1`. `TryParse` rejects any path that can select a set (indexes, wildcards, filters) — a confirmation matching several values has no single truth value — and is checked in `StartAsync`, so a mistyped path is a deploy error rather than "never confirmed" forever. `Evaluate` confirms on the boolean `true` and nothing else. `IsPostProcessingAllowed` holds the three-level rule: a run that threw never reaches it; **unset ⇒ allowed** (the deployed fleet's behaviour, deliberately relaxed); set ⇒ only when confirmed.
- **`MailPostProcessingMode`** (`src/MeshNodes.Sdk/Trigger/`) — the shared vocabulary of the two mail channels: **exactly three** members, `MoveToFolders = 1`, `Delete = 2`, `MarkAsRead = 3`. 🔴 **Every one of them takes the message OUT of the search the next poll runs, and that is the whole mechanism**: nothing in OctoMesh records which mail was already processed — **the mailbox IS the bookkeeping**, and the IMAP search is `NotSeen`. `None = 0` ("leave it where it is") existed once and was a defect: with the per-poll cap (`maxMessagesPerPoll`) it re-fetches the same first N messages on every poll and never reaches the mail behind the cap, so the import runs for ever, reports success and imports nothing new — the shape of an earlier production incident (1697 mails, three pod restarts, no progress). The design specified three modes; the fourth was an artefact of implementing them. Removing it turned both nodes' `else None` fall-through into `MeshAdapterPipelineExecutionException.MailPostProcessingModeNotConfigured`, which names the three valid modes AND the reason. ⚠️ The remaining members keep their numbers: persistence is by NAME on both routes (`ConfigurationSettingsReader.ReadEnum` refuses a purely numeric value, YamlDotNet reads the name), so renumbering would buy nothing. Still nullable on both configurations and still only read through the nodes' `ResolveEffectivePostProcessingMode`, because YamlDotNet lets a PRESENT null key overwrite a property initializer — on a non-nullable enum that would now be the *undefined* zero value; nullable, such a key reads as "unset" and the derivation decides.
- **`MailPostProcessingModeSetting`** (`Nodes/Trigger/`) — the ONE exception to `ConfigurationSettingsReader.ReadEnum`'s rule that an unknown name means "not configured". A **stored `None`** must not take that route: it WAS a storable mode, so a settings entity may still carry it, and degrading it to "not configured" hands the decision to the derivation — which on the accounting seed (`markAsRead: true`) is `MarkAsRead`, i.e. the node would start flagging mail in a mailbox whose operator had asked it to change nothing. So it throws `MailPostProcessingModeRemoved`, naming the attribute, that the mode was removed, the reason, and the channel's own replacement suggestion (IMAP ⇒ `MarkAsRead`, Graph ⇒ `MoveToFolders`). It is thrown from the settings overlay, which both nodes resolve in `StartAsync`, so an operator hears it on deploy. 🔴 **The one route this repo cannot word itself** is a pipeline DEFINITION literally spelling `postProcessingMode: None`: YamlDotNet parses the enum inside octo-communication-sdk's `YamlPipelineConfigurationSerializer` before any adapter code sees the configuration, and the operator gets `Error deserializing pipeline: Exception during deserialization / Requested value 'None' was not found.` — loud and on deploy, but it names neither the key, the node nor the reason. No estate definition spells the mode literally (the accounting seed configures `postProcessingModeAttribute`), so this is hand-made definitions only; wording it properly needs a type converter in the SDK's serializer. Pinned by `MailPostProcessingModeDeserializationTests`.
- **`ConfigurationSettingsReader`** (`Nodes/`) — the settings resolver both mail triggers share. Reads strings, positive ints, zero-tolerant ints (`maxMessagesPerPoll: 0` is a documented "no limit" opt-out and must survive), booleans, round-trip dates and enums BY NAME (a numeric value is refused, so a typo cannot select a mode by ordinal) out of the serialized configuration entity, whose CK attributes sit in a nested `attributes` object. Every reader answers `null` for absent/null/unreadable, which is what makes the overlay rule — **settings win, node property is the fallback** — double as the migration path.
- **`MailPollStatusLine` / `MailPollCounts`** (`Nodes/Trigger/MailPollStatusLine.cs`) — the ONE status line both mail triggers report after every poll and from their failure path, through `ITriggerContext.ReportStatusAsync` (octo-communication-sdk) → the adapter hub's `ReportPipelineStatusAsync` (octo-sdk) → the controller, which writes ONLY the pipeline's `StatusMessage`. Its shape is a contract with the accounting app's import cards: a leading ISO-8601 UTC timestamp (`2026-09-26T17:40:12Z`), or `ERROR ` + timestamp on a failed poll, then mailbox, effective source folder and the counts or the exception text, `" · "`-separated; whitespace/line breaks collapsed, the tail cut at 500 characters (the controller caps at 1000). Never credentials, never message bodies. The call never throws and never blocks the loop — a controller predating the method drops the line server-side, the SDK reporter logs a delivery failure at Debug once per five minutes. Tests: `Nodes/Trigger/MailPollStatusLineTests.cs`.
- **`TriggerStatusLine` / `TriggerStatusThrottle`** (`Nodes/Trigger/`) — the status line of the non-mail triggers (`FromSignal@1`, `FromTeamsBot@1`) in the SAME contract as `MailPollStatusLine` (leading UTC timestamp or `ERROR ` + timestamp, then a subject — bridge number / messaging route — and the text, `" · "`-separated, cut at 500), plus the throttle that decides which events become a report: first event, success↔error transition, activity (after `activityInterval`) or heartbeat. Thread-safe (Teams handles activities concurrently). Tests: `TriggerStatusLineTests`, `TriggerStatusThrottleTests`, `FromSignalNodeStatusTests`, `FromTeamsBotNodeStatusTests`.
- **`AttachmentContentType`** (`Nodes/Trigger/`) — single answer to "is this attachment a PDF?" for every inbound channel. The shared Stage Document pipeline decides that from the **declared** MIME type and routes anything but `application/pdf` through its image-to-PDF branch, which REPLACES the stored bytes with a render of an `<img>` tag: a PDF declared as `application/octet-stream` — which many senders do — is therefore not mislabelled but **destroyed** (a 90402-byte invoice stored as a 5606-byte blank page in production, with the mail already flagged read; 43 of that mailbox's 303 current-fiscal-year mails are declared this way). Keys on the `.pdf` extension first, falls back to the `%PDF-` magic header. Returns **canonical lower-case** for an already-declared PDF, because the stager's gate is an exact string comparison and `application/PDF` would land in the image branch too. `FromMicrosoftGraphEmailNode` has normalised it for a long time and `FromEmailNode` as well; they share this helper so the answer cannot drift apart per transport again.
